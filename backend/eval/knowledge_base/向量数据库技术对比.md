## 二、索引算法深度解析

### 2.1 HNSW（Hierarchical Navigable Small World）

**原理**：构建多层图结构，上层稀疏、下层稠密，搜索时从顶层快速定位到局部区域，再逐层细化。

**核心参数**：
- `M`：每层最大连接数（默认16），影响召回率和内存
- `efConstruction`：构建时探索因子（默认200），影响索引质量
- `efSearch`：搜索时探索因子（默认100），影响QPS和召回率

**性能数据（百万级向量）**：
| M值 | 召回率 | QPS | 内存占用 |
|-----|--------|-----|---------|
| 8 | 0.91 | 3500 | 基准 |
| 16 | 0.97 | 2200 | +40% |
| 32 | 0.99 | 1200 | +80% |

**面试要点**：
> "HNSW 是一种近似最近邻（ANN）算法，通过构建多层图实现对数级搜索复杂度。底层原理是 Small World Graph 的导航性——大多数节点只需少量跳数即可互联。"

### 2.2 IVF（Inverted File Index）

**原理**：将向量空间划分为 N 个聚类（Voroni cells），搜索时只扫描最近的 K 个聚类。

**核心参数**：
- `nlist`：聚类数量（通常 1024~65536）
- `nprobe`：搜索时检查的聚类数（召回率和速度的权衡）

**公式**：
```
搜索范围 = nprobe / nlist
```

### 2.3 DiskANN（微软开源）

**原理**：基于图的磁盘友好索引，将图存储在 SSD 上，通过 PQ（Product Quantization）压缩向量。

**优势**：支持十亿级向量，内存占用仅为内存索引的 1/10。

**论文**：_"DiskANN: Fast Accurate Billion-point Nearest Neighbor Search on a Single Node"_ (SIGMOD 2019)

### 2.4 索引算法对比

| 算法 | 召回率 | QPS | 内存占用 | 适用规模 |
|------|--------|-----|---------|---------|
| **HNSW** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ | 百万~千万 |
| **IVF-Flat** | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | 百万 |
| **IVF-PQ** | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ | 亿级 |
| **DiskANN** | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | 亿级以上 |
| **PUCK** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ | 千万~亿级 |

## 三、主流向量数据库深度对比

### 3.1 Milvus

**架构**：分布式云原生设计，支持 Mishards 代理层实现水平扩展。

**核心特性**：
- 支持 GPU 加速（HNSW on GPU）
- 丰富的标量过滤（JSON、数组、范围）
- 成熟的生产经验（数百家企业使用）

**版本演进**：
- Milvus 1.x：单节点，去中心化
- Milvus 2.x：云原生，CDC 支持
- Milvus 2.4+：GPU HNSW、DiskANN 支持

**实测性能（100万 x 768维向量）**：
```
HNSW (M=16, ef=200):
  - 召回率: 0.973
  - QPS:  2200 req/s
  - 延迟: P99 = 12ms
  - 内存: 8.5 GB
```

### 3.2 Qdrant

**优势**：
- Rust 实现，性能极佳，内存安全
- 支持"多向量"检索（一个文档多个向量）
- 原生支持过滤条件
- 易于部署（Docker 单容器即可生产）

**Payload 过滤**：Qdrant 最强大的特性之一，支持在向量检索的同时进行标量过滤，无需预过滤。

**面试要点**：
> "Qdrant 使用 Rust 编写，在性能和安全性上有天然优势。它的 payload 索引支持在向量搜索时同时做条件过滤，这是很多其他数据库做不到的。"

### 3.3 Weaviate

**核心差异**：原生支持"向量 + 知识图谱"混合检索。

**GraphQL API**：提供类 GraphQL 的查询接口，前端友好。

**模块化设计**：
- `text2vec-*`：支持多种 Embedding 模型
- `qna-*`：支持问答模块
- `reranker-*`：内置重排序支持

### 3.4 Chroma

**定位**：轻量级嵌入式向量数据库，主要用于 AI 原生应用。

**特点**：
- Python-first 设计
- 可以直接嵌入应用进程（进程内模式）
- 适合 RAG 应用的快速原型

**局限**：
- 不支持真正的分布式
- 生产环境需要配合 API 服务使用

## 五、技术细节：距离度量

### 5.1 常用距离度量

| 度量方式 | 公式 | 适用场景 |
|---------|------|---------|
| **余弦相似度** | 1 - cos(θ) | 文本、语义检索（最常用） |
| **欧氏距离** | L2 norm | 图像特征、图像embedding |
| **点积** | A · B | 当需要区分向量长度时 |
| **曼哈顿距离** | Σ\|ai-bi\| | 特定场景 |

**面试回答**：
> "RAG 场景通常用余弦相似度，因为它关注的是方向（语义）而非绝对值。Embedding 模型训练时通常用余弦作为相似度目标。"

### 5.2 量化技术

**PQ（Product Quantization）**：将高维向量分割成多段，每段独立做 K-Means 聚类（典型 8bit），压缩率 8~32x。

**SQ（Scalar Quantization）**：将 float32 压缩为 int8，压缩率 4x，精度损失约 1~3%。

**面试要点**：
> "PQ量化通过将高维向量分段聚类，大幅压缩存储空间。典型做法是 768 维向量分成 8 段，每段 96 维各做 256 类聚类。这样一个向量从 768*4 bytes 压缩到 8 bytes，压缩率 96x。"

## 六、在 RAG 系统中的实践

### 6.1 典型配置（Milvus + BGE）

```python
# Milvus HNSW 配置示例
create_params = {
    "index_type": "HNSW",
    "metric_type": "COSINE",  # RAG 场景首选
    "params": {
        "M": 16,           # 召回率和内存的平衡
        "efConstruction": 200,  # 索引构建质量
        "efSearch": 128    # 搜索质量（越大越准但越慢）
    }
}
```

### 6.2 分片策略

**按 ID 范围分片**（适合有明确 ID 结构的场景）：
```
Shard 1: doc_id % 4 == 0
Shard 2: doc_id % 4 == 1
...
```

**按语义分片**（适合文档类别差异大的场景）：
```
Shard 1: 技术文档类
Shard 2: 产品文档类
Shard 3: 客服知识库
```

### 6.3 元数据过滤

```python
# 实战：只检索最近3个月更新的文档
results = collection.search(
    data=[query_vector],
    anns_field="vector",
    param={"metric_type": "COSINE", "params": {"ef": 128}},
    expr="update_date >= '2024-01-01'",
    limit=10
)
```

## 七、性能调优经验

### 7.1 内存溢出（OOM）问题

**原因**：HNSW 的 `efConstruction` 过高 + 批量建索引时的内存峰值。

**解决方案**：
- 分批建索引（每批 50 万向量）
- 使用 IVF-PQ 代替纯 HNSW
- 开启 DiskANN 将图溢出到 SSD

### 7.2 召回率低

**自检步骤**：
1. 检查 Embedding 模型是否与检索场景匹配（中文用中文模型）
2. 调高 `efSearch`（从 100 提到 256 或 512）
3. 开启混合检索（向量 + BM25）补充关键词召回
4. 考虑使用 Reranker 重排序

### 7.3 延迟高

**优化路径**：
1. `efSearch` 过高 → 适当降低（召回率损失 < 2% 的范围内）
2. 网络问题 → 使用同 Region 部署
3. CPU 瓶颈 → 使用 GPU 加速（HNSW-on-GPU）
4. 向量维度高 → 用 PCA 或 PQ 降维压缩

## 八、面试高频问题

**Q: 向量数据库和传统数据库的区别是什么？**
> 传统数据库做精确匹配（WHERE id=1），向量数据库做近似搜索（找最相似的K个）。背后的数据结构完全不同——传统数据库用 B+Tree，向量数据库用 HNSW/IVF 这类 ANN 图或倒排索引。

**Q: 为什么不用精确搜索（KNN）？**
> 精确搜索的时间复杂度是 O(n)，在大规模向量场景下不可用。ANN 通过近似换时间，召回率损失通常 < 5%，但速度提升 100~1000 倍。

**Q: HNSW 的 ef 参数是什么意思？**
> ef 是 exploration factor，控制搜索时探索的邻居数量。ef 越大，召回率越高，但延迟也越高。生产环境通常在 64~512 之间调优。

**Q: 如何选择距离度量？**
> RAG/文本场景用余弦相似度（语义相似）；图像/特征匹配用欧氏距离；需要区分向量"强度"时用点积。
