# SmartQA 面试文档修复与统一 - OpenSpec
> 版本: 1.0 | 日期: 2026-05-20 | 目标: 让项目文档达到“可展示、可追问、可维护”的面试标准

---

## 1. 目标 (Goal)

修复当前项目中影响面试展示的文档问题，重点解决以下三类风险：

1. 编码污染导致的中文乱码、字符串损坏、展示不专业
2. 文档、脚本、代码、账号、指标之间口径不一致
3. 面试手册信息过多但缺少“当前展示版”的稳定闭环

最终交付一套 **编码正常、口径统一、可直接演示** 的文档资产，供候选人在面试时使用。

---

## 2. 当前问题基线 (2026-05-20)

### 2.1 已确认问题

- `docs/interview-showcase.html` 存在明显乱码，不适合直接展示
- `README.md`、`docs/INTERVIEW_GUIDE.md`、`docs/ai_engineer_learning_path.md` 存在编码污染
- 部分前端源码中中文字符串已污染，但前端仍可构建，说明是“显示层损坏”而非主链路彻底损坏
- 文档中默认账号与后端实际初始化账号不一致
- 文档中的指标规模、测试数量、知识库规模存在多套说法

### 2.2 已确认仍可用的部分

- 核心 Python 文件可通过 `py_compile`
- 前端可成功执行 `npm run build`
- 仓库已有多份 OpenSpec 风格文档，可沿用现有结构

---

## 3. 需求清单 (Requirements)

### REQ-1: 全仓文档编码统一为 UTF-8 [P0]

**描述:** 修复当前所有面试相关文档的编码污染，确保浏览器、编辑器、终端中显示一致。

**范围:**

- `README.md`
- `docs/interview-showcase.html`
- `docs/INTERVIEW_GUIDE.md`
- `docs/ai_engineer_learning_path.md`
- 如修复过程中发现直接被这些文档引用的其他展示文档也存在乱码，应一并处理

**验收标准:**

- [ ] 上述文件全部以 UTF-8 编码保存
- [ ] 中文标题、段落、表格、按钮文案显示正常
- [ ] 浏览器打开 `docs/interview-showcase.html` 无乱码
- [ ] Markdown 文件在本地预览和 GitHub 渲染中均可正常阅读

---

### REQ-2: 面试口径统一 [P0]

**描述:** 所有对外展示材料只保留一套“当前展示版”事实，不允许同一项目出现多套相互冲突的数据。

**需要统一的字段:**

- 默认账号与密码
- 角色数量与角色范围
- 知识库文档数 / chunk 数
- RAG 指标
- 测试规模与测试状态
- 演示步骤数量

**验收标准:**

- [ ] `README.md`、`docs/interview-showcase.html`、`docs/INTERVIEW_GUIDE.md` 三处口径一致
- [ ] 账号信息必须与 `backend/app/main.py` 的实际初始化逻辑一致，或同步修改代码与文档
- [ ] 所有指标标注数据来源与日期
- [ ] 对无法确认真实性的数据，删除或标注“待重跑 / 待更新”

---

### REQ-3: 面试手册收敛为“展示版” [P0]

**描述:** `docs/interview-showcase.html` 应从“大而全资料墙”收敛为“面试展示手册”。

**原则:**

- 优先展示当前能稳定演示的能力
- 删除或降权未经验证的承诺
- 每个亮点都能追溯到代码、脚本或报告

**必须保留的模块:**

- 项目一句话介绍
- 技术栈
- 系统架构
- RAG 主链路
- Agent / LangGraph
- RBAC
- SSE / 审批 / 澄清
- Demo 流程
- 常见追问
- 当前展示版指标

**验收标准:**

- [ ] 首页 30 秒内可让面试官理解项目做了什么
- [ ] 每个核心亮点都能对应到真实文件或真实能力
- [ ] 删除明显过时、重复、冲突、无法证明的内容
- [ ] 手册中的所有账号、指标、流程均能在仓库内找到依据

---

### REQ-4: 学习路线降级为“辅助准备材料” [P1]

**描述:** `docs/ai_engineer_learning_path.md` 保留，但不能再承担“项目真实性证明”的角色。

**处理策略:**

- 保留学习结构和知识路线价值
- 删除或修正“59 个测试全通过”这类无法证实的表述
- 明确它是“学习路线 / 面试准备材料”，不是当前交付状态报告

**验收标准:**

- [ ] 标题与导语清晰说明其用途
- [ ] 删除与当前项目真实状态冲突的结论性表述
- [ ] 编码正常可阅读

---

### REQ-5: README 改为“面试友好版入口” [P1]

**描述:** `README.md` 应成为面试官和协作开发者进入项目的第一入口。

**建议结构:**

1. 项目简介
2. 核心能力
3. 技术栈
4. 快速启动
5. 默认账号
6. 演示入口
7. 关键文档链接

**验收标准:**

- [ ] README 首屏无乱码
- [ ] 3 分钟内读者可知道如何启动项目、如何登录、看什么文档
- [ ] 链接到 `docs/interview-showcase.html`、`docs/INTERVIEW_GUIDE.md`

---

### REQ-6: 建立文档真实性审计规则 [P1]

**描述:** 给编码 agent 一个明确规则，避免“修完编码后继续保留错误口径”。

**审计规则:**

- 文档里出现的数字、账号、文件名、脚本名，必须能在仓库中找到依据
- 若找不到依据，则：
  - 删除
  - 改为保守表述
  - 标注“待验证”

**验收标准:**

- [ ] 所有修订过的文档完成一次自审
- [ ] 修订说明中列出“删除了哪些无法证实的说法”

## 4. 非需求 (Non-Requirements)

以下内容不在本次文档修复范围内：

- 不要求本次顺带重构后端业务逻辑
- 不要求本次重写前端交互
- 不要求本次新增完整自动化测试体系
- 不要求本次重跑全部评估，只需要对现有展示文案做真实性收敛
- 不要求引入新的文档站点框架

## 5. 实施步骤 (Implementation Plan)

### Step 1: 编码修复

- 扫描并修复面试相关 Markdown / HTML 文档乱码
- 必要时修复面试展示涉及的前端中文文案

### Step 2: 事实对账

- 对账代码、脚本、README、面试手册中的：
  - 账号
  - 指标
  - 文档数量
  - 测试数量
  - 演示步骤

### Step 3: 手册收敛

- 将 `docs/interview-showcase.html` 调整为“当前展示版”
- 保留能稳定证明的亮点
- 去掉未验证或互相冲突的内容

### Step 4: README 与辅助材料重写

- 重写 `README.md`
- 修订 `docs/INTERVIEW_GUIDE.md`
- 修订 `docs/ai_engineer_learning_path.md`

### Step 5: 自审与交付

- 浏览器打开 HTML 手册检查
- 核对 Markdown 渲染效果
- 输出一份“修复内容摘要 + 未解决风险”

---

## 6. 给编码 Agent 的执行要求

你需要：

1. 优先修复编码与展示问题，再处理文案统一
2. 不要凭感觉保留数字，凡是无法在仓库中证实的口径，一律改为保守说法
3. 不要新增“看起来很强”的表述来替代乱码
4. 修复后用浏览器或可替代方式验证 HTML 展示结果
5. 最终提交时说明：
   - 修了哪些文件
   - 统一了哪些口径
   - 删除了哪些无法证实的说法
   - 还剩哪些风险未处理
