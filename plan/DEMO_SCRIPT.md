# SmartQA 面试演示脚本（供应链场景）

> 面试时直接打开这个文件，按步骤操作即可。
> 演示前务必先看底部的「演示检查清单」。

---

## 1. 开场白（30秒）

话术参考：

"我来演示一下我做的这个项目——SmartQA，一个面向制造业供应链场景的 RAG + Multi-Agent 智能问答助手。

背景是这样的：我之前在一家光电制造企业实习，参与过 ERP 系统的需求调研和供应链流程梳理。我发现供应链部门每天面对大量重复性查询——库存够不够、采购单到哪了、新供应商要什么资质——这些信息散落在 ERP、制度文件、邮件里，找起来很费时间。

所以我做了这个系统，把供应链的知识文档统一入库，员工用自然语言提问就能获得准确答案，需要查实时数据时自动调用后端系统。

技术栈是 FastAPI + Vue3 + Milvus + Redis + PostgreSQL，通过 Docker Compose 部署。我先跑几个问题您看一下效果。"

---

## 2. 核心演示（5-8分钟）

### Query 1：知识库问答（RAG 检索）

**输入：** `新供应商准入需要什么资质？`

**预期效果：**
- 系统从知识库中检索「供应商管理手册」相关片段
- 生成结构化回答，包含资质审查、样品测试、现场审核三步流程
- 回答下方显示引用来源
- 意图标签显示"知识库问答"，置信度 > 0.8

**可讲知识点：**
- "这里用的是混合检索——先走向量相似度（BGE Embedding），再走 BM25 关键词匹配，两路结果做融合排序"
- "检索到的候选文档会经过 BGE-Reranker 做精排，过滤掉低相关性的片段"
- "如果 Reranker 服务不可用，有降级策略，直接用向量检索的分数排序返回"

---

### Query 2：Query Cache 演示（重复查询）

**输入：** `来料检验发现不良品怎么处理？`（先问一次），然后再问一次同样问题

**预期效果：**
- 第一次：正常走 RAG 检索，回答包含 IQC 检验流程、不合格品处理方式
- 第二次：Query Cache 命中，消息头部出现 ⚡ 缓存命中 标签，毫秒级返回
- 回答下方无 token_usage（缓存接口零 token）

**可讲知识点：**
- "Query Cache 用 MD5(query) 做 key，5 分钟 TTL，LRU 淘汰"
- "相同 query 直接返回缓存结果，省掉 Embedding 计算 + 向量检索 + LLM 生成"
- "面试追问：Cache 粒度是 query 级别，不是 chunk 级别，所以命中率取决于用户重复提问的概率"

---

### Query 3：工具调用 — 库存查询

**输入：** `帮我查一下物料MAT-001的当前库存`

**预期效果：**
- 系统识别为工具调用意图
- 调用 query_inventory 工具，返回物料库存数据（名称、数量、安全库存、状态）
- 工具调用区域默认折叠，只显示一行 `query_inventory ✓`
- 点击可展开查看输入输出详情

**可讲知识点：**
- "这里走的是意图路由，先用规则匹配（关键词：查、库存、物料），快速分流"
- "规则匹配不到才会走 LLM 分类，节省 token 成本"
- "工具调用遵循 ReAct 模式——LLM 先思考需要什么工具，再执行，再根据结果生成回答"
- "这个工具目前返回模拟数据，生产环境对接 ERP 库存模块的 API"

---

### Query 4：工具调用 — 订单查询

**输入：** `采购单PO-20250101到货了吗？`

**预期效果：**
- 识别为订单查询工具调用
- 返回采购单状态（供应商、审批状态、金额、预计到货日期）

**可讲知识点：**
- "展示多工具支持能力，每个工具独立注册，参数和返回格式自描述"
- "工具注册是插件化的，新增工具只需要实现接口、注册到工具列表即可"
- "ReAct 循环最多迭代 5 次，防止死循环"

---

### Query 5：混合意图 — RAG + 工具

**输入：** `物料MAT-003库存不足，帮我建个采购申请工单`

**预期效果：**
- 系统识别为混合意图（先查知识库了解采购流程，再调用 create_ticket 工具）
- 创建工单，返回工单号

**可讲知识点：**
- "这是混合意图场景——用户既需要知识库问答（采购流程），又需要工具调用（创建工单）"
- "意图路由器会识别为 hybrid 类型，先走 RAG 检索回答流程问题，再调用工具创建工单"
- "这种多步任务体现了 Multi-Agent 的协同能力"

---

### Query 6：Token 成本追踪

**输入：** `安全库存的计算公式是什么？`

**预期效果：**
- RAG 检索库存管理制度，返回安全库存公式
- 回答下方显示 token 用量标签：`XXX tokens · ¥0.XXXX · deepseek-chat`

**可讲知识点：**
- "每次 LLM 调用都会追踪 token 用量和费用，基于各模型的实时定价计算"
- "这个数据前端实时展示，后端也写入日志，用于成本监控和优化"
- "DeepSeek 的定价是 input ¥1/百万token，output ¥2/百万token"

---

### Query 7：反馈闭环 + 多轮对话

**输入（接上一轮）：** `那呆滞料怎么定义？`

**预期效果：**
- 系统理解上下文（接续库存管理话题）
- 从知识库检索呆滞料定义（超6个月未动→预警→降价处理）
- 回答后点击 👍 按钮，显示"感谢反馈"

**可讲知识点：**
- "对话记忆存在 Redis 中，最近 10 轮直接保留，超过 10 轮自动压缩为摘要"
- "用户反馈存入 PostgreSQL，评估页面展示满意度趋势"
- "形成数据驱动的优化闭环：发现问题 -> 定位原因 -> 优化 -> 验证"

---

### Query 8：供应商信息查询（新工具展示）

**输入：** `帮我查一下供应商SUP-001的资质信息`

**预期效果：**
- 系统识别为工具调用意图
- 调用 `query_supplier` 工具，返回供应商详情：名称、类别、信用等级、资质认证、账期、平均交期、合作年限
- 展示工具调用区域（可折叠）

**可讲知识点：**
- "新增 `query_supplier` 工具只需要：① 实现 async def 函数，② 加 `@tool` 装饰器，③ 注册到 TOOL_REGISTRY，共 3 步"
- "工具系统是插件化的，LLM 通过函数签名和 docstring 自动理解工具用途，不需要额外配置"
- "这里展示了工具调用的扩展性——从 5 个工具扩展到 6 个，核心代码零改动"

---

### Query 9：Semantic Router 对比演示

**输入 A：** `帮我查下MAT-006的库存` → 规则匹配（<1ms）  
**输入 B：** `我们的供应商评估体系是怎么运作的` → 语义路由（<10ms）

**预期效果：**
- 输入A：意图标签显示"工具调用"，路由方式"rule_match"
- 输入B：意图标签显示"知识库问答"，路由方式"semantic_route"
- 两者响应时间差异明显（可从 DAG 面板查看）

**可讲知识点：**
- "这就是三级路由的威力——90%+ 的请求在前两级解决，不消耗一个 token"
- "语义路由预计算了每个路由类型的代表向量，用户请求来了直接余弦相似度比较，<10ms"
- "面试追问：为什么不直接用 LLM 分类？因为 LLM 分类每次 2.5s + 消耗 token，而这里是本地向量计算"

---

### Query 10：Self-RAG 过滤演示

**输入：** `公司股东结构是什么？`（故意问知识库里没有的内容）

**预期效果：**
- 检索到若干 chunk，但 Self-RAG 过滤后相关性均低
- 系统回复"知识库中未找到相关信息"或"建议联系管理员补充文档"
- 置信度低于阈值（<0.3），触发置信度路由的"低置信度"分支

**可讲知识点：**
- "传统 RAG 会把检索到的内容不管好坏全给 LLM，Self-RAG 让 LLM 先评判每个 chunk 与问题的相关性"
- "相关性评分 <0.3 的 chunk 会被过滤掉，避免用无关内容'胡说八道'"
- "这是减少幻觉的核心机制之一——宁可说'不知道'，也不用低质量内容生成答案"

---

### Query 11：操作审批演示（防误操作）

**输入：** `帮我给 MAT-003 库存不足问题创建一个紧急采购工单`

**预期效果：**
- 系统解析出意图：创建工单，参数齐全
- 前端显示确认弹窗（approval_request）："您确定要执行以下操作：创建工单 [紧急] MAT-003库存不足？"
- 点击「确认执行」后，工具执行，返回工单号 TK-xxxxxxxx
- 点击「取消」则不执行

**可讲知识点：**
- "写操作（Create/Update/Delete）执行前必须人工确认，防止 LLM 误判导致脏数据"
- "这个机制参考了 Hermes Agent 的命令审批流——AI 决策，人类最终确认"
- "面试追问：为什么读操作不需要审批？因为查询是幂等的，不会改变系统状态"

---

### Query 12：澄清提问演示（Clarification）

**输入：** `库存够不够`（故意给一个参数不完整的问题）

**预期效果：**
- 系统识别到意图是库存查询，但缺少「物料编码」参数
- 系统不硬猜，主动回复："您好，请问您想查询哪个物料的库存？请提供物料编码（如 MAT-001）"
- 用户回复 `MAT-001` 后，系统调用工具返回结果

**可讲知识点：**
- "不确定时主动追问，而不是胡乱猜测一个物料——这是对用户体验和数据准确性的负责"
- "澄清判断用语义理解，不是硬编码规则——'库存够不够'/'现货有么'/'还剩多少'都能识别为同类缺参数情况"
- "这个机制避免了工具调用时因参数错误导致的报错或无意义结果"

---

### Query 8：Semantic Router — 规则匹配 vs 语义路由

**输入：** `库存够不够？`

**预期效果：**
- 系统不调 LLM，直接路由到 query_inventory 工具（规则匹配命中"库存"关键词）
- 意图标签显示"规则匹配"，耗时 <1ms，token 消耗为 0
- 对比：换成"我手头的料能不能撑到下个月"这类模糊表达，会走语义路由（Embedding 相似度）

**可讲知识点：**
- "90% 请求在前两层就解决了，不需要调 LLM。语义路由用 BGE-small-zh 在本地算 Embedding，<10ms，零 token"
- "为什么不用纯 LLM 分类？因为语义路由 <10ms + 零 token，LLM 要 2.5s + token 成本"
- "规则匹配是正则，语义路由是预计算向量 + 余弦相似度，两者都不调用外部 API"

**追问应对：**
> "规则匹配和语义路由哪个优先级更高？"
"规则匹配优先（<1ms），因为它零延迟。如果规则没命中，再走语义路由。两个都是本地计算，不走外部 API。"

---

### Query 9：Self-RAG 过滤 — 减少幻觉

**输入：** `采购供应商年度评估什么时候开始？`

**预期效果：**
- 系统检索到 3 个候选 chunk（供应商准入、评估流程、质量考核）
- Self-RAG 判断：只有"评估流程"chunk 相关性 > 0.3，其余过滤
- 回答只基于过滤后的 1 个 chunk 生成，引用来源显示 `[1]`
- DAG 面板"Reranker精排"节点显示相关性评分

**可讲知识点：**
- "传统 RAG 把所有检索结果都丢给 LLM，不管是否相关。Self-RAG 让 LLM 自己判断每个 chunk 的相关性（0-1 分），低于 0.3 的过滤掉"
- "这样做的好处是：减少无关信息对 LLM 的干扰，降低幻觉，同时节省 token 成本"
- "如果 Reranker 服务挂了，有降级策略——直接用向量检索分数排序，不卡死"

**追问应对：**
> "Self-RAG 和普通 Reranker 有什么区别？"
"Reranker 是用专门的排序模型（这里用的 BGE-Reranker）把所有候选重新排序，取 top-K。Self-RAG 是在此基础上多了一层 LLM 相关性判断，0-1 分，过滤低质 chunk 后再生成。"

---

### Query 10：DAG 可视化 — 流水线透明可见

**输入：** 展开"RAG 处理流程"面板，发送任意查询

**预期效果：**
- DAG 面板默认折叠，点击展开显示 6 个节点：意图路由 → 查询理解 → 向量检索 → BM25检索 → Reranker精排 → 答案生成
- 每个节点实时更新状态：灰色"等待中"→ 蓝色"运行中"→ 绿色"完成"（带耗时）
- 节点间连线颜色随状态变化

**可讲知识点：**
- "DAG 节点默认折叠，不干扰正常对话。只有用户主动展开才显示"
- "后端在每个阶段完成时发送 SSE 事件，前端实时更新节点状态和耗时"
- "6 个节点的耗时分布可以看出瓶颈在哪——比如向量检索耗时过长，说明 Embedding 模型需要优化"
- "节点顺序和 RAG 流程一致：路由 → 检索 → 精排 → 生成"

**追问应对：**
> "DAG 数据是从哪里来的？"
"后端 chat.py 在处理请求时，每个阶段完成后把 `{node, status, duration_ms}` 封装成 SSE 事件发到前端。前端解析事件，驱动 Vue 响应式更新。"

---

### Query 11：操作审批 — 防止误操作的写操作确认

**输入：** `帮我创建一个采购申请工单，物料是 MAT-003，数量 500`

**预期效果：**
- 系统识别为写操作（create_ticket），发送 `approval_request` SSE 事件
- 前端弹出确认框，显示：工具名、操作内容、预估影响
- 点击"确认执行"后，工具真正调用，返回工单号 TK-xxx
- 若点击"取消"，返回"已取消"

**可讲知识点：**
- "只有写操作（create_ticket）会触发审批，读操作（query_inventory/query_order）直接执行"
- "审批通过后，带 `approved: true` 重新发送请求，后端验证后才能执行写操作"
- "这是参考 Hermes Agent 的命令审批机制，防止 Agent 误执行不可逆操作"
- "前端把消息文本改成'确认执行：xxx' 重新发送是旧做法，现在用结构化字段 `approved: true`"

**追问应对：**
> "如果用户多次点击确认按钮怎么办？"
"后端有幂等检查——工单号由时间戳+纳秒生成，重复提交会因 UNIQUE 约束失败。也可以在后端加锁，但当前用 ID 生成策略已经解决。"

### Query 12：澄清提问 — 参数不全时主动追问

**输入：** `库存够不够？`

**预期效果：**
- 系统识别为 query_inventory 意图，但缺少必需参数 material_code
- 不硬猜，不报错，直接回复："请问您想查询哪个物料的库存？可以提供物料编码（如 MAT-001）或物料名称。"
- 意图标签显示"澄清提问"，工具调用区域为空

**可讲知识点：**
- "这是参考 Hermes Agent 的 clarify 机制——不确定就问，比猜错更可靠"
- "澄清逻辑是轻量级的正则匹配，不是 LLM 判断。如果正则命中但参数缺失，就主动问用户"
- "query_inventory 的必需参数是 material_code，支持 MAT-xxx 格式或物料名称（轴承、液压油等）"
- "参数齐全后，用户补全信息重新发送，Agent 记住之前的澄清上下文，继续执行"

**追问应对：**
> "澄清和重试有什么区别？"
"澄清是参数缺失时主动问用户，不消耗 token。重试是参数有了但检索质量不好，用不同 query 重新检索。两者时机不同。"

## 3. 架构讲解（3-5分钟）

### 系统架构图

```
用户浏览器
    |
    v
Vue3 前端 (port 3000)
    |  Vite 代理
    v
FastAPI 后端 (port 8001)
    |
    +-- 意图路由 (Router Agent)
    |       |
    |       +-- 规则匹配 (关键词/正则, 零延迟)
    |       +-- 语义路由 (Embedding 相似度, <10ms, 零 token)
    |       +-- LLM 分类 (兜底, 2.5s + token 成本)
    |
    +-- RAG Agent
    |       |
    |       +-- Query 理解 (specific/ambiguous/broad)
    |       +-- 混合检索 (Milvus 向量 + BM25)
    |       +-- RRF 融合排序 (Reciprocal Rank Fusion)
    |       +-- Self-RAG 过滤 (LLM 判断 chunk 相关性)
    |       +-- 父子文档扩展 (小块检索 + 大块送 LLM)
    |       +-- 语义切片 + 引用溯源 [1][2]
    |       +-- 三层置信度路由 (直接/改写重试/Web搜索)
    |       +-- Faithfulness 幻觉检测
    |
    +-- Tool Agent (ReAct 模式)
    |       |
    |       +-- 库存查询 / 订单查询 / 创建工单
    |
    +-- PII 脱敏 (三层防护)
    +-- Token 成本追踪 (实时计费)
    +-- 对话记忆 (Redis + 摘要压缩)
    +-- 反馈闭环 (PostgreSQL)
    |
    v
Milvus (向量库) | Redis (缓存/记忆) | PostgreSQL (元数据/反馈)
```

### 关键设计决策

| 决策 | 方案 | 原因 |
|------|------|------|
| 检索策略 | 混合检索 (向量+BM25) | 向量擅长语义，BM25 擅长关键词精确匹配 |
| 精排模型 | BGE-Reranker | 中文效果好，开源免费 |
| 意图路由 | 规则 → 语义路由 → LLM 三级 | 规则零延迟 + 语义路由<10ms零token + LLM兜底 |
| 工具调用 | ReAct 循环 | 可解释性强，支持多步推理 |
| 对话记忆 | Redis + 摘要压缩 | 读写快，摘要控制 token 消耗 |
| PII 脱敏 | 三层防护 | 文档层 + 查询层 + 日志层，不依赖开发者自觉 |

### 量化指标

- 知识库：12 篇供应链制度文档，200+ 语义切片（按段落/标题边界切分）
- RAG 检索置信度：58-65%（中等置信度，触发 Query 改写重试或直接生成）
- Prompt 迭代：v1→v2 去除 AI 套话，答案冗余率降低约 40%
- Token 成本：单次 RAG 查询约 ¥0.005（DeepSeek 定价，含改写重试）
- PII 覆盖：8 种类型（身份证/手机/邮箱/银行卡/姓名/地址/固话/IP）
- 检索方法：向量 + BM25 → RRF 融合 → Self-RAG 过滤 → 父子文档扩展
- 置信度路由：高(>0.7)直接生成 / 中(0.3-0.7)改写重试 / 低(<0.3)Web搜索
- 意图路由：规则匹配(<1ms) + 语义路由(<10ms, 零token) + LLM分类(2.5s, 兜底)
- Faithfulness：关键词覆盖率检测，score<0.5 时警告

## 4. 常见追问应对

### Q: 如何处理长文档？

"文档上传后按 1000 字符切片，相邻切片有 200 字符重叠，避免跨切片信息丢失。切片前会先做 PII 脱敏。切片后通过 BGE 模型生成 512 维向量，存入 Milvus。"

### Q: 如何评估检索质量？

"三个维度：离线评估（给定 ground truth 计算 Recall@K、MRR、NDCG）、在线评估（基于 rerank_score 分布判断检索质量）、LLM-as-Judge（用大模型评判答案的正确性/相关性/幻觉程度）。评估页面可以实时跑。"

### Q: Prompt 迭代做了什么优化？

"两个版本：v1 是通用 RAG prompt，发现输出经常带'根据参考资料'、'希望对您有帮助'这类套话；v2 在 prompt 里明确禁止这些句式，同时加了后处理正则兜底。低置信度时用更严格的 prompt，禁止建议性语句。两层防御确保输出干净。"

### Q: Token 成本怎么控制的？

"三个措施：规则匹配优先（问候/简单查询不走 LLM，零 token）、Embedding LRU 缓存（相同 query 不重复计算）、对话摘要压缩（超过 10 轮自动压缩，控制上下文长度）。每次调用实时追踪 token 用量和费用。"

### Q: 如何防止大模型幻觉？

"三道防线：第一，Prompt 严格约束'只基于参考资料回答'；第二，低置信度时用更严格的 Prompt，禁止客套话和建议性语句；第三，答案后处理清除 AI 套话。"

### Q: 生产环境怎么部署？

"Docker Compose 一键部署，7 个容器（Milvus/etcd/MinIO/Redis/PostgreSQL + 管理界面）。前端 Nginx 反向代理，后端 uvicorn 多 worker。健康检查端点 /health 检查全链路服务状态。"

### Q: 工具调用怎么实现的？

"两套实现并存：手写 ReAct 循环（默认）和 LangChain AgentExecutor（可切换）。

手写版：LLM 输出 JSON 格式的 Thought/Action/Observation，解析后执行工具，最多迭代 5 次。优势是可控性强。

LangChain 版：用 create_react_agent + AgentExecutor，复用同一套工具。优势是标准化，能证明框架使用经验。

通过 AGENT_TYPE=langchain 或请求参数切换。生产环境用手写版，演示时可切到 LangChain 展示框架能力。"

### Q: 为什么用 BGE 而不是 OpenAI Embedding？

"两个原因：一是数据安全，企业内部文档不适合发给外部 API；二是成本，BGE 模型本地部署，embedding 计算零边际成本。bge-small-zh-v1.5 只有 90MB，CPU 就能跑，512 维向量够用。"

### Q: 权限管理怎么做的？

"RBAC 三级角色：admin（全部权限）、manager（可上传/删除知识库）、employee（只能查询）。密码用 PBKDF2-SHA256 哈希，Token 存 Redis 有 24 小时过期。启动时自动创建默认管理员 admin/admin123。"

### Q: Guardrails 内容安全怎么做？

"两层过滤：输入层用白名单（50 个供应链关键词），问题不在业务域内直接拦截；输出层用黑名单（28 个敏感词），LLM 回答包含敏感内容时用 * 替换。纯关键词匹配，零延迟，不依赖外部模型。"

### Q: 意图路由怎么做的？

"三级路由策略，逐层升级：

第一层，规则匹配（<1ms）：用正则和关键词匹配问候、工具调用等明确意图，零延迟零 token。

第二层，语义路由（<10ms）：预计算每个路由类型的代表 query 的 Embedding 向量，用户 query 来了直接算余弦相似度。相似度 >0.55 就直接路由，不需要调 LLM。90% 的请求在这两层就解决了。

第三层，LLM 分类（2.5s）：只有前两层都匹配不到时才调 LLM，作为兜底。

面试追问：为什么不用纯 LLM 分类？因为 LLM 分类每次要 2.5 秒 + 消耗 token，而语义路由用本地 Embedding 模型（BGE-small-zh，90MB），<10ms 完成，零 token 成本。"

### Q: DAG 可视化是什么？

"前端用纯 SVG 绘制 RAG 处理流水线：意图路由→查询理解→向量检索→BM25→Reranker→答案生成，6 个节点实时显示状态和耗时。后端在每个阶段完成时发送 dag_progress SSE 事件。默认折叠不干扰对话。"

### Q: Self-RAG 是什么？

"传统 RAG 把所有检索结果都丢给 LLM，不管是否相关。Self-RAG 让 LLM 自己判断每个 chunk 与问题的相关性（0-1 分），过滤掉低于 0.3 分的噪音。比如检索到 3 个 chunk，只有 1 个真正相关，就只用那 1 个生成回答，减少幻觉。"

### Q: 父子文档检索怎么做的？

"检索阶段用小 chunk（512 字符）做精确匹配，生成阶段用大 chunk（同章节完整内容）提供上下文。这样兼顾检索精度和生成质量。比如命中'供应商管理手册第 2.1 节'，会自动扩展为第 2 节完整内容送给 LLM。"

### Q: 澄清提问是什么机制？

"参考 Hermes Agent 的 clarify 工具。当用户查询缺少必要参数时（如说'库存不够了'但没说哪个物料），系统不硬猜，主动问用户'请问查哪个物料的库存？'。用 LLM 语义判断是否需要澄清，不靠硬编码关键词。"

### Q: 操作审批怎么做的？

"写操作（如创建工单）执行前，系统发送 approval_request SSE 事件，前端显示确认按钮。用户点击'确认执行'后才真正调用工具。防止误操作，类似 Hermes Agent 的命令审批机制。"

## 5. 技术亮点（面试加分点）

### 双模式 Agent：手写 ReAct + LangChain

"系统同时支持两种 Agent 实现：
1. **手写 ReAct**（默认）：Thought→Action→Observation JSON，最多 5 轮，完全自定义
2. **LangChain AgentExecutor**（可切换）：create_react_agent 标准化实现

两种实现返回格式一致，上层调用无感知。选手写是因生产环境需精确控制；集成 LangChain 是为证明框架使用经验。"

### 置信度架构设计

"置信度分三个维度：
1. **意图分类置信度**：规则匹配是确定性的，不需要置信度；LLM 分类的置信度来自模型输出
2. **检索质量置信度**：基于 rerank_score 的 sigmoid 映射，将任意范围的分数映射到 0-1
3. **生成质量置信度**：通过 LLM-as-Judge 评估答案的正确性、相关性、幻觉程度

三个来源各不相同，避免了硬编码假数据。"

### RAG 降级策略

"生产系统必须有降级策略：
- **Reranker 降级**：模型不可用时，退化为纯混合检索（向量 + BM25），不崩溃
- **Embedding 降级**：模型加载失败时，向量检索不可用，但 BM25 关键词检索仍可工作
- **LLM 降级**：API 超时时，返回预设的兜底回答

每层降级都有明确的日志标识，方便排查问题。"
