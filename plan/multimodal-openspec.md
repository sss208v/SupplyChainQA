# SmartQA 多模态增强 — OpenSpec 需求规格

> 版本: 1.0 | 作者: Hermes | 日期: 2026-05-13

---

## 1. 现状盘点

### 1.1 当前能力：纯文本 RAG

SmartQA 目前是一个**纯文本** RAG 系统：

- 输入：用户文本 query
- 检索：文本 embedding（bge-large-zh-v1.5）→ Milvus 向量检索 + BM25
- 生成：LLM 基于文本 context 生成文本回答
- 前端：textarea 输入框，不支持文件/图片上传

**全项目搜索 "image/vision/multimodal/VLM/图片" 只有两处注释：**
- `knowledge.py:245` 「支持图片提取和描述（需VLM配合）」— 愿望，无代码
- `data_preprocess.py:4` 「业务数据（文本/图片）」— 提到但不处理图片

### 1.2 缺少什么

| 能力 | 当前 | 面试价值 |
|------|------|----------|
| **图片输入**（用户上传产品照片/截图，问「这是什么」） | ❌ | 高——展示多模态 RAG |
| **PDF 图片提取**（从 PDF 中提取图表/流程图并描述） | ❌ | 中——完整的文档理解 |
| **图片 embedding**（用 CLIP 等多模态模型做图搜图） | ❌ | 高——多模态检索 |
| **VLM 理解**（用 GPT-4V/Claude 3.5 Vision 理解图片内容） | ❌ | 高——前沿技术展示 |
| **多模态混合检索**（文本+图片混合 result，统一排序） | ❌ | 高——架构扩展能力 |

### 1.3 面试验证过的加分项

来自真实面试面经（快手/字节/腾讯等）：
- 「你们支持图片问答吗？」— 常见追问
- 「PDF 里的图表怎么处理的？」— 文档解析的深度追问
- 「有没有考虑多模态？」— 高频考察技术视野

## 2. 需求分析

### REQ-1: 图片上传 + VLM 理解（核心闭环）[P0]

**描述:** 用户可以在对话中上传图片，后端调用 VLM（Vision Language Model）理解图片内容，将图片描述注入 RAG pipeline，支持两种模式：

1. **图片问答**（独立）：用户上传图片 + 提问 → VLM 直接回答（不经过 RAG）
2. **图片增强 RAG**（混合）：用户上传图片 + 提问 → VLM 生成图片描述 → 以图片描述作为额外检索 query → RAG 检索 + 原图描述一起送入生成

**技术方案:**
- 前端：`ChatInput.vue` 增加图片上传按钮（支持粘贴/拖拽/点击上传）
- 后端：`POST /api/v1/chat/upload-image` 接收图片，存到 `backend/uploads/images/`
- VLM：使用 MiniMax 的 vision API（已有 MiniMax API key，不引入新供应商）
- 流程：图片 → base64 → MiniMax Vision API → 文本描述 → 送入 LLM 生成

**为什么是 P0:** 这是多模态最直观的体现，面试时一句话能讲清楚：「支持图片上传，比如拍一张物料照片问系统这是什么物料」。

**验收标准:**
- [ ] 前端聊天输入框增加图片上传按钮（Element Plus 的 `el-upload`）
- [ ] 图片预览（缩略图显示在输入框上方，可删除）
- [ ] `POST /api/v1/chat/stream` 支持 `images: List[str]`（base64 或 URL 列表）
- [ ] 后端新增 `core/vision.py`：封装 MiniMax Vision API 调用
- [ ] 图片描述注入 RAG pipeline（作为额外检索 query 或 context 前缀）
- [ ] SSE 事件增加 `vision_result` 类型，前端展示「图片分析中...」
- [ ] 支持常见格式：JPEG、PNG、WebP

**面试价值:**
「我们用 MiniMax Vision API 做图片理解——用户上传产品照片、ERP 截图、质检报告，系统先用 VLM 理解图片内容，然后把文字描述送入 RAG 检索相关文档。这样图片和文本知识库就打通了。」

**阻塞项:** MiniMax Vision API 的可用性和成本需要验证。

---

### REQ-2: PDF 图片提取与描述 [P1]

**描述:** 文档解析时，利用 opendataloader-pdf 的图片提取能力（JSON 输出含 bounding box + 图片 base64），对 PDF 内嵌图片调用 VLM 生成文字描述，嵌入到文档 chunk 中。

**为什么是 P1:** 供应链文档（产品手册、质检报告、流程图）中有大量图表。纯文本提取会丢失这些信息，导致「这个图的流程是什么」无法回答。

**验收标准:**
- [ ] `_read_pdf()` 使用 opendataloader 的 JSON 输出模式（含图片数据）
- [ ] 提取的图片保存到临时目录，调用 VLM 生成描述
- [ ] 图片描述插入到对应 chunk 的 Markdown 中（保持阅读顺序）
- [ ] 可以通过开关 `EXTRACT_PDF_IMAGES=false` 关闭（省 token）
- [ ] 大图片（>5MB）自动跳过，避免阻塞

**面试价值:**
「PDF 解析不只是提文字——我们用 opendataloader 提取内嵌图片，再调用 VLM 生成描述，嵌入到检索索引里。这样图表里的信息也不会丢失。」

---

### REQ-3: 多模态混合检索 [P2]

**描述:** 支持用 CLIP 或类似多模态 embedding 模型对图片做向量化，实现「以图搜图」+「图文混合检索」。

**为什么是 P2:** 这是加分项但不是核心。如果 P0/P1 完成后还有时间，可以做。

**验收标准:**
- [ ] 集成 CLIP 模型（如 `openai/clip-vit-base-patch32`）做图片 embedding
- [ ] 图片入库时自动生成 CLIP embedding + 文本 embedding（双向量）
- [ ] 检索结果支持混合排序（文本相似度 + 图片相似度加权融合）

**面试价值:**
「我们考虑过用 CLIP 做图文混合检索，文本和图片在同一个向量空间里做相似度计算——但当前的业务场景以文本为主，所以作为 P2 扩展。」

---

### REQ-4: 前端多模态交互优化 [P1]

**描述:** 前端需要优雅地展示多模态内容，不只是文本。

**验收标准:**
- [ ] `ChatMessage.vue` 支持渲染图片（Markdown `![alt](url)` 转为 `<img>`）
- [ ] SSE `vision_result` 事件显示加载动画
- [ ] 对话历史中保留图片缩略图
- [ ] 知识库页面显示「含 X 张图片」标签

---

### REQ-5: 面试话术准备 [P1]

**描述:** 更新 `docs/interview-showcase.html`，加入多模态部分。

**验收标准:**
- [ ] 新增「多模态能力」section（方案设计 + trade-off + 实测数据）
- [ ] 准备高频追问的应答话术：
  - 「为什么不用 CLIP？— 当前场景文本为主，但架构支持扩展」
  - 「图片理解延迟多少？— VLM API 约 2-5 秒，可以异步预加载」
  - 「PDF 图片提取准确率？— 取决于 VLM 能力，目前在 85%+」

## 3. 技术风险评估

| 风险 | 等级 | 应对 |
|------|------|------|
| MiniMax Vision API 不可用/太贵 | 🟡 | 新增供应商配置项，支持切换到 OpenAI Vision 或 Claude Vision |
| VLM 调用增加延迟（2-5秒） | 🟡 | 前端显示加载状态，图片描述异步生成后流式追加 |
| PDF 图片太多导致 token 爆炸 | 🟢 | 限制每文档最多 N 张图片 + 大图跳过 |
| CLIP 模型加载增加启动时间 | 🟢 | P2 才做，且可独立开关 |

---

## 4. 优先级总结

```
P0: 图片上传 + VLM 理解（核心闭环，面试必问）
P1: PDF 图片提取、前端交互优化、面试话术
P2: CLIP 多模态检索
```

---

## 5. 不做的事（明确排除）

- ❌ 不做视频理解（供应链场景不需要）
- ❌ 不做音频理解
- ❌ 不做本地 VLM 部署（太重，GPU 成本高）
- ❌ 不做实时摄像头/OCR（超出范围）
- ❌ 不做图片生成（不是问答系统的事）
