Supply Chain QA 是一个后端 FastAPI (14,584 行) + 前端 Vue 3 (7,025 行) 的 RAG + Multi-Agent 项目。 后端 66 个源文件，728 个测试用例；前端 29 个源文件，62 个测试用例。 本次评审从模块深度、职责分离、测试性三个维度筛查出以下改进机会。

发现项

1️⃣

chat.py — 巨型文件（1225行），职责杂糅

Strong

📁 涉及文件

backend/app/api/chat.py (1225行) backend/app/api/chat_helpers.py

问题：chat.py 同时承担了 11 种职责——SSE 传输协议、意图路由分发、RAG 检索（从 Query理解到 LLM生成的完整流程）、Redis缓存（Query Cache+分布式锁+幂等）、置信度路由、图融合、CLIP 多模态、工具权限检查、写审批、性能指标收集、对话记忆。其中 event_generator() 约 900 行，内部 7 个意图分支用硬 if/elif 分立。RAG_ANSWER 分支约 350 行几乎完整重写了 agents/rag.py 的核心流程。

📈 影响

两处 RAG 流程不同步：chat.py 无 CRAG 重试，rag.py 有
单元测试困难：需 mock 大量外部依赖
新人理解成本高：一个文件理解整个对话链路

💡 推荐方案

将 event_generator() 按意图分支拆为独立 handler（如 _handle_rag_answer()、_handle_tool_call()），核心 RAG 逻辑复用 rag_agent.answer()，API 层只做路由分发+SSE 包装。

2️⃣

全局单例模式泛滥，耦合严重、测试困难

Strong

📁 涉及文件

agents/rag.py core/rag/engine.py core/evaluator.py core/milvus_client.py core/neo4j_client.py core/redis_client.py

问题：几乎所有核心模块都在模块加载时创建全局单例（rag_agent = RAGAgent()、rag_engine = RAGEngine()、milvus_manager = MilvusManager()…），且这些单例互相引用。测试无法通过构造替换依赖，只能通过 mock.patch 拦截模块级变量——这是一种脆弱的测试模式，容易因导入顺序或 patch 未生效导致测试失败。

📈 影响

集成测试时真实服务(milvus/neo4j)未启动→模块级导入异常
单例之间直接 import，依赖关系不透明
无法并发测试（单例状态在不同测试函数间泄漏）

💡 推荐方案

采用依赖注入——函数/类接收外部依赖作为参数。创建一个 DependencyContainer 类来管理所有单例的生命周期，测试时可以构造不同的 container mock。

BEFORE — 模块级全局单例

3️⃣

ChatMessage.vue — 前端超载组件（864行）

Strong

📁 涉及文件

frontend/src/views/Chat/components/ChatMessage.vue (864行)

问题：单个组件处理 15+ 种不同的 UI 状态（意图标签7种、工具调用折叠、Markdown 渲染、参考来源、DAG可视化、写审批、澄清提问、冲突检测、反馈按钮、加载动画、Token用量、缓存命中、CLIP检索、置信度决策、Web搜索、演示模式、性能指标）。模板中 15+ 个 v-if 分支。单一组件承担了消息渲染的全部职责。

📈 影响

修改任一子功能需理解整个864行代码
模板中 15+ v-if 分支令渲染逻辑难以追踪
单元测试覆盖困难：需要构造超复杂的 props

💡 推荐方案

按业务边界拆为子组件：IntentTags、ToolCallPanel、ReferenceSources、FeedbackBar、ApprovalPanel、TokenUsageBadge、MetricsDisplay 等。每个组件＜150行，职责单一。

4️⃣

RAG 流程跨层重复 — Agent vs Engine 职责不清

Strong

📁 涉及文件

backend/app/agents/rag.py (635行) backend/app/core/rag/engine.py (587行) backend/app/api/chat.py event_generator (350行 RAG分支)

问题：RAG 流程散落在三个文件中，职责划分模糊——RAGAgent 叫"Agent"却做了 Query理解、HyDE、子问题生成、CRAG 重试等"Engine"工作；RAGEngine 叫"Engine"却包含了 Graph 融合、Critic 评估等策略性逻辑；chat.py 又有一份独立的 RAG 内联实现。三者对检索结果的处理方式不一致，修改一处逻辑需要改三个文件。

📈 影响

CRAG 重试逻辑仅 rag.py 有，chat.py 和 engine.py 缺失
新增检索策略（如 Query改写）需三处同步修改

💡 推荐方案

明确分层：Engine = 纯数据管道（检索+排序+融合），Agent = 策略层（Query理解→Engine→后处理），API 层只做 SSE 包装。

5️⃣

chat.js Store — 16+ 状态变量与 SSE 紧密耦合

Worth exploring

📁 涉及文件

frontend/src/stores/chat.js (357行) frontend/src/api/chat.js (273行)

问题：chat.js Store 管理 16+ 个独立状态变量（从 messages、streaming 到 demoMode），11 个 SSE 事件回调直接内联修改状态。sendMessage() 通过 messages.value[aiIdx] 直接操作底层数组索引。Store 的职责从"状态管理"扩展到了"SSE 事件解析 + 消息构建"。

📈 影响

11 个内联回调使 sendMessage() 难以阅读和测试
状态分散在 Store 不同字段，引用的消息索引容易越界

💡 推荐方案

将 SSE 事件处理抽象为独立 SSEEventDispatcher，Store 只暴露 actions 接收结构化状态更新。将消息构建逻辑移到辅助函数中，Store 专注于状态管理。

6️⃣

前端硬编码工具 Schema — 前后端不同步

Worth exploring

📁 涉及文件

frontend/src/views/Tools/index.vue backend/app/core/tool_engine.py

问题：前端的 toolSchemas 对象硬编码了 5 个工具的输入/输出 Schema，而后端 TOOL_REGISTRY 有 11 个注册工具。其余 6 个工具（web_search、calculator、code_interpreter、track_logistics、calculate_reorder_point、query_supplier）仅后端存在，前端工具管理页完全没有展示。

📈 影响

新增工具需改前后端两处，容易遗漏
事实来源不明确：前端 Schema 可能与后端不一致

💡 推荐方案

添加 GET /api/v1/tools/schema 端点，从 TOOL_REGISTRY 动态生成 Schema 返回给前端，实现"后端为单一事实来源"。

7️⃣

observability.py — 4 个 record_* 函数模式重复

Worth exploring

📁 涉及文件

backend/app/core/observability.py

问题：4 个 record_* 函数（record_router_decision、record_tool_call、record_rag_retrieval、record_llm_generation）重复完全相同的模式：
① _record_local(…) → ② lf = _get_langfuse() → ③ trace = lf.trace(…) → ④ trace.span(…).end() → ⑤ lf.flush()
每个函数约 20 行，核心差异仅 span name、input/output 字段和 metadata。

💡 推荐方案

抽取通用 _record_span(name, input_data, output_data, metadata) 辅助函数，4 个 record_* 各约 3-5 行即可。

8️⃣

Evaluate 和 Tools 页面组件体积偏大

Speculative

📁 涉及文件

frontend/src/views/Evaluate/index.vue (746行) frontend/src/views/Tools/index.vue (662行)

问题：这两个页面组件均超过 650 行，虽然尚未到 ChatMessage.vue 的程度，但也包含了过多的模板和逻辑。Evaluate 页面混合了 ECharts 图表配置、评估运行控制、结果展示、进度跟踪等多重职责。

💡 推荐方案

将 ECharts 雷达图/柱状图抽取为独立组件，评估结果列表拆为子组件，页面组件只做容器布局。

首选改进建议

先拆分 chat.py（#1），再解耦单例（#2），后拆分 ChatMessage.vue（#3）

理由：chat.py 的 1225 行是后端最大的单一维护痛点。它里面的 900 行 event_generator() 函数包含重复的 RAG 逻辑，是导致前后端数据不一致、测试困难、新人上手慢的核心原因。 拆分 chat.py 能立刻带来三个好处：① 暴露重复的 RAG 流程并统一；② 为后续改依赖注入创造条件（单例数量减少）；③ 每个路由 handler 变得可以独立测试。

预期效果：chat.py 从 1225 行 → ~300 行，移除约 350 行重复 RAG 代码，后端测试从 728 增至 ~800 个（因 handler 可独立测试）。
