模块 1  ·  系统全景 MUST

🏗️ 用最直白的话解释整体架构

这个系统就是一个「智能接线员」：用户提问 → 接线员判断问题类型 → 派给不同专家处理 → 汇总回答。

接线员 = Router（意图路由）
知识专家 = RAG Agent（查文档找答案）
操作专家 = Tool Agent（查库存/订单/建工单）
总调度 = Orchestrator（把多步任务拆给不同专家接力执行）

🧭 RAG 与 Agent 的职责边界 Datawhale

参考 Datawhale all-in-rag / wow-agent 系列教程，RAG 和 Agent 解决的是 两类不同问题：

维度RAG（检索增强生成）Agent（智能体）
核心能力 从知识库检索相关文档，注入 LLM prompt，生成有依据的回答 自主决策调用哪些工具、按什么顺序、何时停止，完成复杂任务
适用场景 「什么是安全库存」「供应商准入流程分几步」——有标准答案的问题 「查 MAT-001 库存，如果不足 200 件就帮我建补货工单」——需要多步推理的问题
SmartQA 实现 RAG Agent：混合检索（Milvus 向量 + BM25 关键词）→ RRF 融合 → Reranker 精排 → LLM 生成 ToolAgent：LangGraph StateGraph + bind_tools，agent↔tools 循环；Orchestrator：Plan→Execute→Summarize 多步编排
面试关键句 「RAG 本身不决策——它只负责找相关文档。Agent 负责根据任务目标决定调用什么工具、调用几次。」 「Agent 可能会多次调用 RAG 作为工具之一——比如先查知识库获取上下文，再调库存工具查实时数据，最后汇总。」
📚 Datawhale 知识：RAG 本质是「检索 + 生成」两步；Agent 本质是「感知 + 决策 + 执行」的循环。在 SmartQA 中，Router 判断意图后，简单知识问答走 RAG 链路，复杂操作走 Agent 链路，两者互补而不是互斥。

① 负责什么

SSE 流式对话的主入口。接收用户提问 → PII 脱敏 → 检查 Query Cache → 调 Router 路由 → 按意图分发给不同 Agent → 通过 async generator 逐 token 推送 SSE 事件给前端。

📚 Datawhale 通用概念（参考 easy-langent）：SSE（Server-Sent Events）是一种基于 HTTP 的单向推送协议，服务端通过 Content-Type: text/event-stream + async generator 逐条推送 data: {json}\n\n 格式的消息。相比 WebSocket，SSE 更轻量且浏览器原生支持自动重连，适合 AI 对话这种「请求→流式响应」的单向场景。在 LangChain/LangGraph 生态里，通常用 FastAPI 的 StreamingResponse 包装 async generator 来实现。

② 为什么重要

这是整个系统的「导演」——所有复杂逻辑的调用入口都在这里。面试官如果问你「一个请求进来后发生了什么」，你讲的 90% 都在这个文件里。

面试官会怎么问
「你的 SSE 是怎么实现的？为什么不用 WebSocket？」
你应该怎么回答
SSE 是单向推送（服务端→客户端），AI 对话场景正好只需要这个方向。FastAPI 的 StreamingResponse + async generator 天然支持 SSE，不需要额外库。相比 WebSocket，SSE 基于 HTTP，兼容所有代理和负载均衡，自动重连。我们定义了 7 种 SSE 事件类型：session / route / content / tool_status / sources / token_usage / conflicts，前端按 type 字段分发渲染。
📌 只需记住 3 个点：
1. chat_stream() 用 async generator + StreamingResponse 实现 token 级流式输出
2. 7 种 SSE 事件类型，前端按 type 分发渲染
3. 写操作（create_ticket）需要前端 approved=true 确认后才执行

② 负责什么

判断用户问题属于哪种意图（问候/RAG/工具/混合/目标型/图谱/不明），路由到对应的处理链路。核心方法 route() 实现了三级级联：规则匹配 → 语义路由 → LLM 分类。

📚 Datawhale 通用概念（参考 easy-langent / wow-agent）：意图路由是 Multi-Agent 系统的入口——不是所有问题都需要 Agent。Datawhale 教程中的典型模式是：先做意图分类（关键词/LLM），再分发给不同 Agent。关键词匹配快但有盲区，LLM 分类智能但慢且贵。工业界的常见做法是「规则优先 + LLM 兜底」——这和我们的一致。

③ 为什么重要

这是面试官最喜欢的「设计决策」问题——为什么不用纯 LLM 路由？为什么不用纯规则？你怎么说服我你的三层设计是合理的？

面试官会怎么问
「为什么路由要分三层？直接用 LLM 判断意图不行吗？」
你应该怎么回答
成本和延迟的权衡。第一层规则匹配覆盖了大部分高频明确意图（「查 MAT-001 库存」「什么是安全库存」），零延迟零 Token。第二层语义路由用 embedding 余弦相似度，<10ms 且同样零 Token。只有前两层都 miss 的模糊问题才走 LLM，约 2.5 秒。这个设计把 Token 消耗压到了最低，同时保证了复杂语义的覆盖。企业级系统常用的做法就是用规则兜底确定性场景，LLM 只做兜底。
📌 只需记住 3 个点：
1. 规则匹配 <1ms 零 Token，覆盖大部分高频明确意图
2. 语义路由用 embedding 相似度，<10ms 零 Token
3. LLM 分类 ~2.5s，只处理前两层 miss 的模糊意图

③ 负责什么

混合检索引擎。核心方法 search()：向量检索（Milvus，top_k=20）+ BM25 关键词检索（top_k=20）→ RRF 融合排序（K=60，自适应权重）→ 低分过滤 + Jaccard 去重 → BGE-Reranker CrossEncoder 精排（top_k=3）→ 冲突检测 → 置信度计算。

📚 Datawhale 通用概念（参考 all-in-rag / wow-rag / easy-vecdb）：
• 向量检索：把文本转成高维向量（Embedding），用余弦相似度或欧氏距离找最近邻。擅长语义匹配，但对精确编码（MAT-001）效果差。
• BM25：经典的词频-逆文档频率算法，擅长关键词精确匹配。不依赖模型，速度快。
• RRF（Reciprocal Rank Fusion）：把不同检索源的排名融合——不比较原始分数（向量分数和 BM25 分数尺度不同），而是比较排名位置。公式：score = Σ 1/(K + rank)，K 控制排名影响的衰减速度。
• Reranker：用 CrossEncoder（而非 BiEncoder）对 query-document 对做精细语义匹配打分，通常用 BGE-Reranker 系列模型。
• SmartQA 参数：RRF_K=60, VECTOR_TOP_K=20, BM25_TOP_K=20, RERANK_TOP_K=3（见 config.py）。

④ 为什么重要

RAG 是系统的核心能力，面试官一定会问你检索链路。混合检索 + RRF + Reranker 是当前 RAG 系统的事实标准。

面试官会怎么问
「为什么不用纯向量检索？加 BM25 和 Reranker 到底有多少收益？」
你应该怎么回答
向量检索擅长语义匹配，但对精确查询（物料编码 MAT-001、订单号 PO-20250601）效果很差——embedding 模型把编码当成无意义字符串。BM25 恰好擅长精确关键词匹配。我们的自适应 RRF 会根据查询类型调整权重：精确查询时 BM25 权重 ×1.5，语义查询时向量权重 ×1.5。Reranker 是用 CrossEncoder 做精排，把 RRF 融合后的 top-N 再做一次 query-document 对打分，比只用 RRF 排序的准确率高。代价是 CPU 推理约 50-100ms。
📌 只需记住 3 个点：
1. 向量(Milvus, top20) + BM25(rank_bm25, top20) → RRF(K=60) 自适应权重融合 → Reranker(CrossEncoder, top3) 精排
2. 自适应 RRF：精确查询（含编码）BM25×1.5，语义查询（含怎么/如何）向量×1.5
3. 后处理链：低分过滤 → Jaccard 去重(>0.7) → 冲突检测(同实体不同数值标记)

④ 负责什么

ToolAgent (tool.py)：LangGraph StateGraph 实现 ReAct 循环。LLM 决策 → 需要工具时由自定义 async 工具执行节点调用 tool.ainvoke() → 结果返回 LLM 继续 → 最多 5 轮收敛。
Orchestrator：跨域工作流编排。Plan（LLM生成计划）→ Execute（按序调专域 Agent）→ Summarize（汇总）。DEMO_MODE 下有确定性本地模板兜底。

📚 Datawhale 通用概念（参考 easy-langent / hello-agents）：
• ReAct（Reasoning + Acting）：LLM 交替进行「思考」和「行动」——先想需要什么工具，再调用工具获取结果，再用结果继续推理。这是 Agent 的基础范式。
• StateGraph（LangGraph）：用有向图定义 Agent 的状态流转——节点是处理函数（如 agent 决策节点、工具执行节点），边是转移条件（如有 tool_calls → 去 tools 节点，无 tool_calls → END）。比 LangChain 的 AgentExecutor 更透明可控。
• bind_tools：LangChain 的 llm.bind_tools([tool1, tool2]) 在 LLM 调用时自动注入工具 schema，让 LLM 输出结构化 tool_calls。
• SmartQA 区别：项目没有用 LangGraph 内置的 ToolNode，而是实现了自定义 async 工具执行节点——直接调用 tool.ainvoke()，绕过 ToolNode 是为了更可控地记录指标（tool_metrics.record）、处理异常和适配已有的 BaseTool。

⑤ 为什么重要

Agent 是系统的「高级能力」——从单轮问答到多步推理的关键跨越。面试官问「你这个多 Agent 到底多在哪里」，答案就在这里。

面试官会怎么问
「你的 ToolAgent 用 LangGraph 的 ToolNode 吗？为什么？」
你应该怎么回答
没有直接用 ToolNode。我们参考了 ToolNode 的思路——在 StateGraph 中加一个 tools 节点处理 tool_calls——但实现了自定义 async 工具执行节点。原因是：第一，ToolNode 内部封装较深，不方便在每次工具调用时记录执行指标（耗时、成功/失败）；第二，我们的工具基于自定义 BaseTool，需要直接调 ainvoke() 来保持接口一致；第三，自定义节点可以更精细地处理异常——工具不存在、执行超时、结果格式异常等，每种情况都有明确的降级行为。代价是约 220 行代码，但完全可控。

模块 4  ·  高频追问与标准回答 关键

Q1: 为什么要用 RAG 而不是直接微调模型？▼
🟡 20 秒短答

供应链的 SOP、供应商资质、库存标准这些知识是频繁更新的。RAG 更新知识库即可，微调需要重新训练。而且 RAG 提供引用溯源，这在企业场景是合规刚需。

🟢 90 秒展开

我们选 RAG 有三个理由。第一，供应链文档更新频繁——今天改一个质检标准，RAG 重新索引就行；微调要重新训练，成本高且无法保证一致性。第二，RAG 给了引用溯源能力——你可以追问「这个答案来自哪个文档第几页」，在企业合规场景下这是必须的。第三，RAG 的幻觉比纯生成模型可控——我们用 BGE-Reranker 精排 + Faithfulness 检测，给出了回答可靠性的量化指标。当然 RAG 的 trade-off 是检索质量决定了回答上限，如果知识库里没有相关文档，RAG 也帮不了你——所以我们加了三层置信度路由，低置信度时自动改写查询或搜索外部信息。

Trade-off：RAG 的检索质量是回答的天花板——知识库没覆盖的内容，RAG 也答不了。
Q2: 为什么要做多 Agent？单 Agent 不能调用多个工具吗？▼
🟡 20 秒短答

关注点分离。采购 Agent 只知道采购工具和知识、仓库 Agent 只知道仓库工具和知识——每个 Agent 的 system prompt 更短，决策更精准，幻觉更少。

🟢 90 秒展开

单 Agent 把所有工具塞给一个 LLM，system prompt 会非常长——工具描述、使用规则、权限边界全混在一起。我们做了两件事：第一，专域 Agent（InventoryAgent、PurchaseAgent 等）各自只暴露自己领域的工具，prompt 精简后推理质量更高。第二，Orchestrator 做跨域编排——当用户说「帮我评估 MAT-001 的库存风险」，Orchestrator 自动拆成「查库存→查在途订单→查供应商→汇总」，每一步调用对应的专域 Agent。这种设计让复杂查询的准确率比单 Agent 直接把所有工具扔给 LLM 高。当然多 Agent 的 trade-off 是编排链路更长，Orchestrator 本身也依赖 LLM 做计划生成，加上专域 Agent 各自的 LLM 调用，Token 消耗比单 Agent 多。

Trade-off：多 Agent 编排链路更长，Token 消耗更多——但对复杂查询的准确率提升是值得的。
Q3: Router 为什么分三层？直接用 LLM 不行吗？▼
🟡 20 秒短答

成本控制。大部分高频明确意图——比如「查 MAT-001 库存」——规则匹配零延迟零 Token 就能处理。只有真正模糊的意图才走 LLM。

🟢 90 秒展开

第一层规则匹配覆盖了大部分常见提问模式——工具关键词、RAG 关键词、问候正则——实测覆盖大部分高频意图。第二层语义路由用 embedding 余弦相似度和预设的示例意图做匹配，<10ms，也零 Token。只有前两层都 miss 时才走 LLM 分类，约 2.5 秒。这是「先规则后模型」的经典设计——企业系统中能用规则解决的绝不浪费 Token。而且规则匹配是确定性的，LLM 分类有一定随机性——对于「查 MAT-001 库存」这种明确意图，规则更可靠。

Trade-off：规则维护需要人工更新关键词表——如果业务领域扩展，需要持续补充规则词典。
Q4: SSE 的价值是什么？为什么不用 WebSocket？▼
🟡 20 秒短答

AI 对话只需要服务端→客户端单向推送，SSE 比 WebSocket 更轻量——基于 HTTP、兼容所有代理、自动重连。

🟢 90 秒展开

SSE 有四个优势：第一，基于 HTTP 协议，不需要升级握手，所有 HTTP 代理和负载均衡天然兼容。第二，浏览器原生支持 EventSource API，自动重连。第三，我们定义了 7 种事件类型（session/route/content/tool_status/sources/token_usage/conflicts），前端按 type 字段分发渲染，比 WebSocket 的消息路由更简单。第四，FastAPI 的 StreamingResponse + async generator 天然支持 SSE，零额外依赖。WebSocket 适合双向实时通信，但对于 AI 对话这种单向流式输出场景，SSE 是更合适的选择。

Trade-off：SSE 只能服务端推送，客户端发消息需要另外的 HTTP 请求——但这正好匹配 AI 对话的请求-流式响应模式。
Q5: 权限怎么做？▼
🟡 20 秒短答

两层权限：PostgreSQL 做认证（UUID Token + Redis），Milvus ARRAY 列做数据级授权（security_group 字段 + array_contains 过滤）。

🟢 90 秒展开

认证层：UUID Token 存在 Redis，24 小时过期，可主动登出失效——比 JWT 的优点是能主动踢人。授权层：每个知识库文档在索引时带上 security_group 字段（如 ["admin","purchase"]），查询时用 Milvus 的 array_contains(security_group, user_role) 过滤——只有用户角色在文档的 security_group 里的内容才会返回。这个设计把权限逻辑推到了数据库层，应用层不需要手动过滤，而且 过滤开销可接受，且把权限下推到底层数据库。BM25 端也有同步的权限过滤。

Trade-off：权限粒度是角色级别的——同一角色的所有人看到的内容一样。细粒度权限需要改 ARRAY 为每个用户维护 visibility 列表。

Q10: ReAct 是什么？你的 ToolAgent 怎么实现的？ Dw▼
📚 Datawhale（参考 easy-langent / hello-agents）：ReAct = Reasoning + Acting。LLM 输出分两段：先「思考」需要什么工具和参数，再「行动」调用工具获取结果，然后带着结果继续推理。这是区别于纯 Chain（固定步骤）的关键——Agent 能根据中间结果动态调整下一步。
🟡 20 秒短答

ReAct 就是让 LLM 边想边做——先判断需要调哪个工具，调完拿到结果后再决定是继续调其他工具还是直接回答。SmartQA 用 LangGraph StateGraph 实现了这个循环。

🟢 90 秒展开

SmartQA 的 ToolAgent（tool.py，约 220 行）实现了一个标准的 ReAct 循环：agent 节点用 bind_tools 让 LLM 输出 tool_calls → tools 节点用自定义 async 执行器调用 tool.ainvoke() → 结果以 ToolMessage 注入对话 → 回到 agent 节点继续推理。最多 5 轮。关键设计：没有用 LangGraph 内置 ToolNode，而是自定义了 async_tool_node——这样可以记录每次工具调用的耗时和成功率（tool_metrics），并对工具不存在/执行失败等异常做明确降级处理。Orchestrator 则是在更高一层做 ReAct 的变体——Plan（思考要分几步）→ Execute（逐步执行，每步结果注入下一步）→ Summarize（汇总输出）。

Trade-off：自定义工具节点比直接用 ToolNode 多约 40 行代码，但换来了完整的指标记录和异常处理——对于需要向面试官展示「工程化」的项目，这个代价值得。
Q11: 为什么用 RRF 融合而不直接加权求和？ Dw▼
📚 Datawhale（参考 all-in-rag / wow-rag）：向量检索返回余弦相似度（0~1），BM25 返回词频分数（无上界，可达数百）。两者的分数尺度完全不同，直接加权求和会严重偏向 BM25。RRF 只关心排名位置——排名第 1 的贡献 1/(K+1)，排名第 100 的贡献 1/(K+100)——天然消除尺度差异。K=60 是经典默认值，控制排名影响的衰减速度。
🟡 20 秒短答

向量分数和 BM25 分数尺度不同（一个是 0~1，一个是无界整数），直接加会偏向 BM25。RRF 只比排名位置不比原始分数，消除了尺度差异。

🟢 90 秒展开

SmartQA 的 rag_engine.py 中 _merge_results() 实现了 RRF 融合：先从两个检索源各取 top-20，为每个 chunk 计算 RRF 分数 = vec_weight/(K+vec_rank) + bm25_weight/(K+bm25_rank)，K=60。然后按 RRF 分数降序排列，取 top-N 给 Reranker。我们还做了自适应权重：查询含编码/数字（精确查询）时 BM25 权重 ×1.5，查询含怎么/如何（语义查询）时向量权重 ×1.5。融合后还有低分过滤（min_rrf=0.008）和 Jaccard 去重两道后处理。

Trade-off：RRF 只考虑排名，丢失了原始分数的置信度信息——如果两个 chunk 分数差距很大但排名相邻，RRF 把它们当成同等重要。但实际场景中这个损失很小，可接受。
Q12: RAGAS 评估了哪些指标？结果怎么解读？ Dw▼
📚 Datawhale（参考 all-in-rag / wow-rag）：RAGAS 是 RAG 系统的主流评估框架，核心指标：Context Precision（检索到的文档是否相关）、Context Recall（相关文档是否被检索到）、Faithfulness（回答是否完全基于上下文而非幻觉）、Answer Relevancy（回答与问题的相关度）。评估需要 (question, contexts, answer, reference) 四元组。
🟡 20 秒短答

我们在 17 条供应链样本上跑了 RAGAS 评估，Faithfulness 和 Context Precision 整体较好，验证了混合检索+精排的方向有效。但样本量小，不能夸大为工业级结论。

🟢 90 秒展开

评估数据在 backend/eval/eval_ragas_result_full_sc.json，17 条供应链领域问答样本。每条包含 user_input、retrieved_contexts、response、reference，以及 RAGAS 计算的四个指标（faithfulness/answer_relevancy/context_precision/context_recall）。从趋势上看，系统在事实性问题（如「供应商需要哪些资质」）上 Faithfulness 很高（1.0），在需要综合多个文档的问题上 Faithfulness 有波动。Context Precision 整体较好说明混合检索找对了文档。面试时要诚实：17 条样本只能证明技术方向有效，不是工业级评估。说「在当前 17 条样本上看出混合检索方向更稳、更有潜力」即可。

Trade-off：17 条样本太小，不能做统计推断。但 RAGAS 框架本身的使用证明了项目具备评估意识——知道"好"的标准并能量化。
Q13: LangChain 和 LangGraph 的分工是什么？ Dw▼
📚 Datawhale（参考 easy-langent）：LangChain 负责「组件」——LLM 调用封装（ChatOpenAI）、工具定义（BaseTool）、消息管理、prompt 模板等。LangGraph 负责「编排」——用有向图（StateGraph）定义 Agent 的状态流转逻辑。简单说：LangChain 提供积木，LangGraph 画图纸。
🟡 20 秒短答

LangChain 管 LLM 调用和工具绑定（bind_tools），LangGraph 管 Agent 的流程编排（StateGraph 定义节点和边）。积木 vs 图纸。

🟢 90 秒展开

在 SmartQA 中，两者的分工非常清晰：LangChain 负责 ChatOpenAI 的 LLM 调用封装、BaseTool 的工具接口标准化、bind_tools 的工具 schema 注入、消息的序列化管理。LangGraph 负责 ToolAgent 的 ReAct 循环编排——StateGraph 定义 agent 节点（LLM 决策）和 tools 节点（工具执行），用条件边和普通边连接它们。三个 Agent 后端（ToolAgent/LangGraphAgent/LangChainAgent）都共享 LangChain 底座，区别在于编排方式——LangGraph 的 StateGraph 更透明可控，AgentExecutor 更标准化但封装更深。面试时说「我们选择 LangGraph 做编排是因为能看到每一步的状态流转，调试和优化都比黑盒 Agent 方便」。

Trade-off：StateGraph 比 AgentExecutor 代码多，但可控性远胜。LangGraph 的学习曲线陡一些，但对于需要给面试官解释清楚每一环的场景，透明度比简洁重要。

1. 这个项目解决什么问题？用一句话说清楚。★
考察：架构 / 演示能力
答案：供应链部门间信息孤岛——用一个自然语言入口打通分散在文档、ERP、数据库里的供应链信息。核心是 RAG 检索 + 多 Agent 工具调用双链路。
陷阱：不要说「这是一个 AI 问答系统」——太泛了，没有领域 specificity。
2. 用户请求从进到出的完整路径是什么？★
考察：架构
答案：前端 POST /chat/stream → PII 脱敏 → Query Cache 检查 → Router 意图路由（规则→语义→LLM）→ 按意图分发（RAG/Tool/Goal/Hybrid）→ SSE 流式逐 token 返回 + sources + token_usage + conflicts 事件。
关键：要说出「意图分发」这个环节——这是系统的核心调度点。
3. RAG 和 Agent 的职责边界是什么？★
考察：架构 / Datawhale
答案：RAG 负责从知识库检索相关文档并生成有引用的回答——不决策，只检索+生成。Agent 负责根据任务目标自主决策调用哪些工具、按什么顺序、何时停止——会多次调用工具包括 RAG。在 SmartQA 中，Router 判断意图后将简单知识问答分给 RAG，复杂操作分给 ToolAgent 或 Orchestrator。
关键：「RAG 不决策，Agent 做决策」——一句话说清楚。
4. 三级路由每一层的特点和触发条件是什么？★★
考察：架构 / trade-off
答案：第一层规则匹配：关键词/正则命中 → 直接返回意图，<1ms 零 Token，覆盖大部分高频明确意图。第二层语义路由：embedding 余弦相似度 → 匹配预设意图示例，<10ms 零 Token。第三层 LLM 分类：前两层 miss 时触发，~2.5s，消耗 Token。
追问：「为什么不直接用 LLM 分类？」→ 成本和延迟。规则匹配是确定性的，LLM 有随机性。
5. RAG 混合检索链包含哪些环节？参数是什么？★★
考察：代码 / 架构
答案：Milvus 向量检索(top_k=20) + BM25 关键词检索(top_k=20) → RRF 融合去重(K=60) → 低分过滤(>0.008) → Jaccard 去重(>0.7) → BGE-Reranker CrossEncoder 精排(top_k=3) → 冲突检测 → 置信度计算。自适应 RRF：查询含编码/数字时 BM25 权重 ×1.5，含怎么/如何时向量权重 ×1.5。
参数来源：全部在 config.py 中定义。
6. ToolAgent 的工具执行节点是怎么实现的？★★
考察：代码
答案：使用自定义 async 工具执行节点（async_tool_node），不是 LangGraph 内置 ToolNode。流程：LLM 输出 tool_calls → 自定义节点遍历每个 tc → 从 tools_by_name 查找工具 → await tool.ainvoke(tool_args) → 记录 tool_metrics（耗时/成功率/异常）→ 构造 ToolMessage 返回。约 220 行。
为什么不用 ToolNode：更可控地记录指标，自定义异常处理，适配已有 BaseTool 接口。
7. Orchestrator 的 Plan→Execute→Summarize 各做什么？★★
考察：架构 / 代码
答案：Plan：LLM 根据预设的 Agent 能力描述生成 JSON 格式执行步骤。Execute：按序调用各专域 Agent，每一步结果注入下一步上下文。Summarize：≤3 步直接模板拼接，≥4 步用 LLM 汇总。DEMO_MODE 下返回确定性本地模板。关键：步骤间上下文传递是核心。
8. 行级权限的实现机制是怎样的？★★
考察：架构 / 工程化
答案：两层：PostgreSQL 做认证（UUID Token + Redis），Milvus ARRAY 列 security_group + array_contains 做数据级过滤。BM25 同步权限检查。权限推到底层数据库过滤——应用层不需要手动遍历结果做权限检查。
9. SSE 和 WebSocket 的区别，为什么你选 SSE？★
考察：架构 / trade-off
答案：SSE 是单向推送（服务端→客户端），AI 对话只需要这个方向。基于 HTTP 无需升级握手、兼容所有代理和负载均衡、浏览器原生 EventSource 自动重连、FastAPI StreamingResponse 零额外依赖。
关键：说出「AI 对话只需要单向推送」——这是选择 SSE 的根本理由。
10. 项目有多少测试？怎么分类？★
考察：工程化
答案：87 个测试函数：81 个纯 Python 单元测试（26s）+ 6 个集成测试（需 Docker）。命令：pytest tests/ -q -k "not integration"。pytest.ini 不含导入依赖。
诚实点：LLM 依赖的集成测试在外网波动时可能失败。
11. 多源冲突检测是怎么实现的？★★
考察：代码 / 架构
答案：在 RAG 检索的 top-5 结果中用正则提取「实体名+数值」对。同一实体在不同 chunk 中出现不同数值时标记为冲突，通过 SSE 推送 conflicts 事件，冲突上下文追加到 LLM prompt。
局限性：只检测同一实体不同数值，不检测语义冲突。
12. 三个 Agent 后端的区别是什么？★★
考察：代码 / 架构
答案：ToolAgent（默认）约 220 行 LangGraph StateGraph，自定义 async 工具节点。LangGraphAgent（多节点循环）Router→Tool→Observe→Decide 四节点。LangChainAgent 使用 AgentExecutor（备选）。三者接口完全一致，共享 LangChain bind_tools 底座，切换只需改 AGENT_TYPE 配置。
生产化选哪个：ToolAgent（代码最少、最可控）。
13. 当前项目最大的风险是什么？你怎么应对？★★★
考察：trade-off / 工程化
答案：最大风险：Agent/Orchestrator 的推理质量依赖外部 LLM，在外网波动或 API key 失效时最亮点的功能无法复现。应对：DEMO_MODE 本地模板降级、Query Cache 复用结果、三层置信度路由减少 LLM 调用。生产化第一优先级：加本地 Ollama 兜底。
为什么这是好答案：这说明你不仅知道系统能做什么，也知道系统在什么条件下不能做什么。
14. 如果面试官问「你这项目有什么技术难度」，你怎么回答？★★★
考察：演示能力
答案：正确的回答：「最大的技术挑战是让多个 Agent 协作时上下文不丢失——Orchestrator 的每一步结果要精确注入下一步的 prompt，如果某一步失败还得保证后续步骤有合理的降级行为。另一个挑战是混合检索的排序质量——向量和 BM25 的分数尺度不同，直接用分数相加会偏向某一方，所以我们用 RRF 排名融合来解决尺度不一致的问题。」
关键：把问题翻译成技术挑战，而不是抱怨「LLM 不稳定」。
15. 从 0 重建这个项目，你会改变什么设计决策？★★★
考察：trade-off / 架构
答案：三个改变：第一，Agent 从设计之初就加入本地模型兜底。第二，Orchestrator 计划生成从纯 LLM 改为规则模板 + LLM 补充的混合模式——大部分供应链场景计划可模板化。第三，SSE 事件类型从前端硬编码改为 schema 驱动。
为什么好：这是「经历了完整开发后对设计有了更深的理解」——面试官最喜欢这种反思。
16. 什么是 Embedding？SmartQA 用了什么模型？ Dw★
考察：Datawhale 基础 / 代码
答案：Embedding 是把文本转成固定维度向量的技术。语义相近的文本，向量距离（余弦相似度）也近。SmartQA 使用 BAAI/bge-small-zh-v1.5（512维），通过 HuggingFaceBgeEmbeddings 加载。Embedding 缓存用内存 LRU（500 条），不用 Redis——因为 Embedding 计算是 CPU 密集型，内存比 Redis 快 100 倍。配置见 config.py: EMBEDDING_MODEL。
面试时：不要只说「用 BGE」，要说清楚「BGE 是 BAAI 的中文优化模型，在中文语义匹配上优于通用模型」。
17. ReAct 的核心思想是什么？SmartQA 的 ToolAgent 如何体现？ Dw★★
考察：Datawhale / 代码
答案：ReAct = Reasoning + Acting：LLM 交替进行「思考」和「行动」。SmartQA 的 ToolAgent 用 LangGraph StateGraph 实现了标准的 ReAct 循环——agent 节点（LLM 决策，输出 tool_calls）→ tools 节点（自定义 async 执行器，调 tool.ainvoke()）→ agent 节点（继续推理）。最多 5 轮收敛。区别于纯 Chain：Agent 能根据中间结果动态调整下一步。
关键区别：自定义 async 工具节点替代 LangGraph 内置 ToolNode，为的是记录指标和异常处理。
18. RRF 解决了什么问题？SmartQA 的 RRF 参数是多少？ Dw★★
考察：Datawhale / 代码
答案：向量检索和 BM25 的分数尺度不同（余弦相似度 0~1 vs BM25 无界整数），直接加权求和会偏向 BM25。RRF 只比较排名位置：score = Σ 1/(K+rank)，K=60。SmartQA 在 rag_engine.py 的 _merge_results() 中实现，还加了自适应权重——精确查询（含编码）BM25×1.5，语义查询（含怎么/如何）向量×1.5。
参数：RRF_K=60（config.py），VECTOR_TOP_K=20，BM25_TOP_K=20。
19. Reranker 为什么能提升准确率？SmartQA 怎么用的？ Dw★★
考察：Datawhale / 代码
答案：RRF 只做排名融合，不直接计算 query-document 的语义相关性。Reranker 用 CrossEncoder（BGE-Reranker-v2-m3）对 query-document 对做精细语义匹配打分，比双向编码器的向量检索准得多。代价是 CrossEncoder 推理慢（每对都要过一次完整模型）。SmartQA 只在 RRF 融合后的 top-N 上做 Reranker 精排，最终取 top_k=3（RERANK_TOP_K）。如果模型加载失败，自动降级为按原始检索分数排序。
面试关键句：「Reranker 是用计算换精度——只在少量候选上做精细匹配。」
20. RAGAS 的四个核心指标是什么？SmartQA 的评估结果怎么用？ Dw★★
考察：Datawhale / 工程化
答案：Faithfulness（回答是否基于上下文）、Answer Relevancy（回答与问题相关度）、Context Precision（检索到的文档是否相关）、Context Recall（相关文档是否被检索到）。SmartQA 在 backend/eval/eval_ragas_result_full_sc.json 中有 17 条供应链样本的完整评估。面试时如实说：17 条样本只能证明方向有效——Faithfulness 在事实性问题上高，在综合问题上波动——样本量小，不能做统计推断。但这证明了项目具备评估意识。
不要说：「我们的 CP 是 0.67」——样本太小没意义。要说「在小样本上验证了混合检索方向有效」。
21. LangChain 和 LangGraph 在 SmartQA 中分别管什么？ Dw★★
考察：Datawhale / 架构
答案：LangChain 管「组件」——LLM 调用封装（ChatOpenAI）、工具定义（BaseTool）、bind_tools 注入工具 schema、消息管理。LangGraph 管「编排」——StateGraph 定义 Agent 的状态流转（agent 节点 → tools 节点 → agent 节点循环）。三个 Agent 后端共享 LangChain 底座，编排方式不同。面试时：「LangChain 是积木，LangGraph 是图纸——我们选择 LangGraph 做编排因为状态流转完全透明，每一步都看得到。」
22. 向量数据库和传统数据库的核心区别？SmartQA 为什么选 Milvus？ Dw★★
考察：Datawhale / trade-off
答案：传统数据库按精确值查询（WHERE name='MAT-001'），向量数据库按语义相似度查询（找和「库存不足」语义最接近的文档）。核心差异是索引算法——向量数据库用 HNSW/IVF 等近似最近邻算法，在亿级向量上实现毫秒级检索。SmartQA 选 Milvus 因为：开源且 CNCF 毕业项目、支持 ARRAY 列做标量过滤（行级权限）、gRPC 高性能连接、和 LangChain 有现成集成。PostgreSQL 的 pgvector 也能做向量检索但性能和规模不如专用向量数据库。
面试关键：「选 Milvus 不是因为它是'最好的'，而是它同时满足了向量检索+标量过滤（行级权限）两个需求。」
