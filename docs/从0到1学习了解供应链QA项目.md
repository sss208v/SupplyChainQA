## 先建立整体认知

### 1.1 供应链 QA 是什么

供应链 QA 是一个面向制造业供应链的企业级智能问答系统。员工用自然语言提问，系统自动路由到两条链路之一：

- **RAG 链路**：知识类问题（"安全库存标准是多少"）走多路混合检索，从 90+ 篇部门制度文档中检索并生成有引用来源的回答。
- **Agent 链路**：业务类问题（"查一下 MAT-001 的库存"）走 LangGraph ReAct 工具调用，实时查询库存/订单/供应商/工单等业务数据。

它不是一个"上传 PDF 问问题"的 Demo。它重点展示的是企业级 RAG 应用背后的工程骨架：

- 如何做三级意图路由（规则 -> 语义 -> LLM 兜底），让绝大多数请求不消耗 LLM 调用。
- 如何做三路召回（Milvus 向量 + BM25 关键词 + Neo4j 图谱）并用类型感知 RRF 融合。
- 如何用 CRAG（检索质量评估 + Query 改写重试）和 Self-RAG（LLM 逐 chunk 相关性过滤）提升回答质量。
- 如何用 4 层缓存把重复查询从秒级降到毫秒级，并保证知识库变更后不读脏数据。
- 如何用 Milvus `security_group` ARRAY 列做行级 RBAC，让不同部门只能检索到自己可见的文档。
- 如何用 SSE 把检索 DAG 进度、来源、置信度决策、token 用量实时推给前端。
- 如何用 JWT + Redis 黑名单做无状态认证 + 可主动登出。
- 如何在写操作（建工单）前做澄清检查、权限校验、人工审批、幂等抢占和分布式锁。
- 如何用 Langfuse 做 span 级全链路追踪。

一句话总结：

> 供应链 QA 是一个可运行、可测试（1000+ 单测）、可扩展的企业级 RAG + Multi-Agent 系统，核心价值是把意图路由、混合检索、质量反思、多层缓存、行级权限和流式可观测串成一个完整闭环。

### 1.2 先看总架构

不需要一开始就理解每个细节，先记住五个区域：

```Plain Text
┌────────────────────────────────────────────────────────────────┐
│  前端 Vue3 + Element Plus + Pinia（6 个页面）                    │
│  Login / Dashboard / Chat / Knowledge / Tools / Evaluate       │
└──────────────────────────┬─────────────────────────────────────┘
                           │ HTTP + SSE（vite 代理 / nginx 反代）
┌──────────────────────────▼─────────────────────────────────────┐
│  API 层  backend/app/api/                                      │
│  chat.py（路由分发）→ handlers/（7 种意图各一个 handler）        │
│  knowledge.py / tool.py / auth.py / evaluate.py / feedback.py  │
├────────────────────────────────────────────────────────────────┤
│  Agent 层  backend/app/agents/                                 │
│  router.py 三级意图路由 · rag.py RAGAgent 统一检索管线          │
│  tool.py ToolAgent(ReAct) · orchestrator.py 多步编排           │
├────────────────────────────────────────────────────────────────┤
│  核心引擎  backend/app/core/                                    │
│  rag/engine.py 混合检索 · cache_manager.py 4层缓存门面          │
│  tool_engine.py 11个工具 · text_to_sql.py · graph_engine.py    │
│  auth.py JWT+RBAC · milvus/neo4j/redis_client.py               │
└──────┬──────────┬──────────┬──────────┬──────────┬─────────────┘
       │          │          │          │          │
   Milvus      Neo4j      Redis    PostgreSQL   SQLite        llama.cpp
   向量库      图谱库    缓存/记忆    用户/元数据  业务模拟库    本地LLM(18080)
```

- **前端**：JavaScript（不是 TypeScript），所有 HTTP 请求经 `src/api/request.js` 统一封装并自动带 JWT。
- **API 层**：`chat.py` 只做路由分发和公共前置，业务逻辑在 `handlers/` 下按意图拆分。
- **Agent 层**：策略层。RAGAgent 决定"怎么检索"，ToolAgent 决定"调哪个工具"。
- **核心引擎**：数据管道层。真正执行检索、缓存、SQL、图查询的地方。
- **基础设施**：docker-compose 编排 10 个服务；LLM 由 llama.cpp 本地部署（OpenAI 兼容接口）。

### 1.3 推荐学习路线

建议按四个阶段推进。

**第一阶段：跑通项目。**

先不要读 `rag/engine.py`，里面同时包含缓存、降级、重试、融合、精排逻辑。先按第 3 章跑起来，用前端问一个问题，看 SSE 事件在浏览器 Network 面板里怎么流动。

**第二阶段：读主链路。**

从 `api/chat.py` 的 `chat_stream()` 进入，顺着 `event_generator()` -> 意图路由 -> `handlers/rag_answer.py` -> `rag_agent.prepare_retrieval()` / `execute_retrieval()` -> `rag_engine.search()` 这条线读。第一遍只看主干，跳过所有 try/except 降级分支。

**第三阶段：拆子系统。**

主链路看明白后，再分别读：

- `agents/router.py`：三级意图路由怎么在 <1ms / <10ms / ~秒级 三档之间递进。
- `core/rag/engine.py`：三路召回、RRF 加权、低分过滤、Jaccard 去重。
- `core/rag/critic.py` + `agents/rag.py` 的 CRAG 段：检索质量评估和 Query 改写重试。
- `core/llm_relevance.py`：Self-RAG 逐 chunk 过滤。
- `core/cache_manager.py` + `core/semantic_cache.py`：4 层缓存与失效。
- `core/auth.py` + `core/milvus_client.py` 的 `build_visibility_expr()`：认证与行级 RBAC。
- `core/tool_engine.py` + `agents/tool.py`：工具注册表与 ReAct 循环。
- `core/text_to_sql.py`：NL2SQL 的五层安全防护与自纠正。
- `core/neo4j_client.py`：模板化 Cypher 与 2-hop 子图检索。

**第四阶段：做扩展实验。**

至少做四个小实验（第 9 章有详细步骤）：

- 新增一个只读业务工具并注册到 `TOOL_REGISTRY`。
- 新增一篇部门知识文档并验证 RBAC 可见性。
- 给某个 handler 补一个降级路径单测。
- 调整一个 RRF 权重参数并用 `backend/eval/` 评估集验证影响。

### 3.2 配置环境变量

复制模板并按需修改：

```Plain Text
copy .env.example backend\.env
```

最关键的几组配置（完整清单看 `backend/app/config.py`，它是所有参数的单一事实来源）：

```Plain Text
# LLM：llama.cpp 本地部署，OpenAI 兼容接口
LLM_PROVIDER=local
LOCAL_LLM_BASE_URL=http://localhost:18080/v1
LOCAL_LLM_MODEL=Qwen3-14B

# JWT（必填，>=32 字节；不配则 PyJWT 报 InvalidKeyError）
JWT_SECRET=<openssl rand -hex 32 生成>

# 认证边界：本地演示允许匿名对话；生产必须 true
REQUIRE_AUTH_CHAT=false

# 无 LLM 时的降级演示模式
DEMO_MODE=false
```

RAG 与缓存的默认参数（config.py 实际值，面试时不要背错）：

```Plain Text
CHUNK_SIZE=256  CHUNK_OVERLAP=128
RRF_K=90  VECTOR_TOP_K=60  BM25_TOP_K=60  RERANK_TOP_K=12
RRF_MIN_SCORE=0.012（必须 < 最小单路分数 1.25/90≈0.0139，否则纯向量召回被全过滤）
RRF 权重：precise 时 BM25=1.25 / semantic 时向量=2.25 / default BM25=1.75 向量=1.25
SEMANTIC_CACHE：阈值 0.92 / TTL 600s / 上限 200 条（阈值可用 scripts/tune_router_thresholds.py 离线调参）
SEMANTIC_ROUTER：阈值 0.65（支持 per-intent 覆盖）/ margin 0.03（top1-top2 分差低于此值回退 LLM）
L1_CACHE：256 条 / 300s    L3_CACHE：SQL 60s / 工具 30s
Self-RAG 阈值 0.15  CRAG_ENABLED=true  CONFIDENCE_THRESHOLD=0.6
图谱融合：GRAPH_FUSION_ALPHA=0.5（RRF 权重）BETA=0.7（图谱权重）
```

## 一次请求的完整链路

### 4.1 主链路总览

以 `/api/v1/chat/stream` 一次 RAG 问答为例：

```Plain Text
用户输入
  -> 前端 stores/chat.js 发起 fetch，携带 Authorization: Bearer <JWT>
  -> 限流中间件（Redis 滑动窗口，故障降级内存）
  -> chat.py chat_stream()：
       PII 脱敏（data_filter）
       认证（REQUIRE_AUTH_CHAT=true 时未登录直接 401；从 JWT 解析 user_role/user_id）
  -> event_generator() 公共前置：
       DEMO_MODE 提示 -> Langfuse trace -> session 事件
       -> Query Cache 检查（md5(query:role)，命中则零 token 重放并 return）
  -> 意图路由 router.route()：规则匹配(<1ms) -> 语义路由(<10ms) -> LLM 分类兜底
  -> 按意图分发到 handlers/ 下对应 handler（7 选 1）
  -> RAG_ANSWER handler：
       rag_agent.prepare_retrieval()   # Query 分类 + 复杂度分析 + HyDE/子问题
       -> milvus.build_visibility_expr(role)   # 行级 RBAC 表达式
       -> rag_agent.execute_retrieval()        # 三路召回 + CRAG + Self-RAG（to_thread 隔离）
       -> 冲突检测 / CLIP 图像检索（可选）
       -> 置信度路由：>=0.6 直答 / 0.3~0.6 改写重检 / <0.3 Web 搜索补充
       -> LLMFactory.astream() token 级流式生成（熔断器 + 重试包裹）
       -> 关键词覆盖率护栏（<0.5 发 coverage 警告）
       -> 结果写回 Query Cache -> sources / performance_metrics 事件
       -> 对话记忆写入 Redis（按 user_id 隔离）
  -> yield "data: [DONE]"
```

### 4.2 数据形态如何变化

理解链路时不要只看函数调用，要看数据形态：

```Plain Text
用户问题字符串
  -> PII 脱敏后的 safe_query
  -> 意图路由结果 {intent, confidence, method, tool_name?}
  -> 检索准备 prep {query_type, rrf_query_type, search_queries[], strategy_config}
  -> 引擎检索结果 {results[], confidence, conflicts[], retrieval_method}
  -> CRAG/Self-RAG 过滤后的 unique_results[]
  -> 上下文字符串 context_str + 来源列表 sources[]
  -> System Prompt（模板 + 对话历史 + context）
  -> LLM 流式 chunk -> SSE content 事件
  -> 完整回答 full_content -> Query Cache JSON -> 对话记忆条目
```

### 4.3 七种意图与对应 handler

| 意图 | handler | 处理方式 |
|---|---|---|
| GREETING | greeting.py | 规则应答，不走 LLM |
| UNCLEAR | unclear.py | 轻量检索兜底：搜到则 LLM 回答，搜不到给引导建议 |
| RAG_ANSWER | rag_answer.py | 完整 RAG 管线（本文档主角） |
| TOOL_CALL | tool_call.py | 澄清检查 -> RBAC -> 写操作审批 -> 幂等+分布式锁 -> ReAct（最多 5 轮） |
| GOAL | goal.py | Orchestrator 拆解多步计划并逐步执行（120s 超时） |
| HYBRID | hybrid.py | RAG 检索 + 工具调用双路结果融合生成 |
| GRAPH_QUERY | graph_query.py | Neo4j 模板化 Cypher 图谱推理 |

设计要点：handler 全部是"纯函数式 async generator"——依赖通过参数注入、只 yield SSE 事件字符串、不持有状态，因此每个 handler 都可以 mock 依赖独立单测。

### 4.4 SSE 事件类型

前端按 `type` 字段分发渲染，常见事件：

```Plain Text
session / trace / demo_mode        # 会话与可观测元信息
cache_hit                          # Query Cache 命中（零 token 重放）
route                              # 意图路由结果（intent/method/耗时）
dag_progress                       # 检索 DAG 各节点进度（前端画流程图）
query_analysis                     # 复杂度分析（light/standard/full）
llm_relevance                      # Self-RAG 逐 chunk 评分
conflicts                          # 多源数值冲突提示
confidence_decision                # 三层置信度路由决策
web_search                         # 低置信度外部搜索补充
content                            # token 级回答增量
sources                            # 引用来源 + 置信度
token_usage / coverage             # 用量成本 / 幻觉护栏警告

error -> data: [DONE]              # 异常与结束标记
```

CLAUDE.md 硬约束：聊天接口必须是 SSE，不允许改成 WebSocket 或普通 JSON。

## 核心模块分析

### 5.1 三级意图路由（agents/router.py + core/intent_routes.py）

路由解决的问题：不是所有请求都值得走完整 RAG 或 LLM。设计成三级递进（hybrid routing，与业界 semantic-router 思路一致）：

1. **规则层（<1ms）**：只做确定性短路，按优先级依次匹配：问候 -> **实体编码优先**（MAT-/PO-/TK- 编码 + 关系词 -> graph_query；编码前缀 + 领域提示词 -> tool_call）-> 精确工具命令词 -> 目标型关键词 -> 高精度知识问句正则。注意：旧版的 100+ 领域泛词大表（"库存""采购"等）已删除——它会抢在语义层之前碰撞误判（如 "MAT-001 还剩多少库存" 被泛词"库存"短路成 RAG）。
2. **语义层（<10ms）**：覆盖率主力。embedding 余弦相似度匹配 5 类意图样本（rag_answer/tool_call/greeting/goal/graph_query），两道门槛：分数 >= 阈值（全局 0.65，per-intent 可覆盖）且 top1-top2 分差 >= margin 0.03（分差过小视为模糊），不满足则回退 LLM。
3. **LLM 分类（~2.5s）**：前两级都不确定时才回退到 LLM 分类（本地 llama.cpp，零 token 成本，只有延迟成本），带工具名防幻觉校验。

**配置化是这个模块的关键设计**：关键词/实体规则/语义样本全部外置在 `app/data/intent_routes.json`，由 `core/intent_routes.py` 加载：按 mtime 热加载（改关键词不用重启），工具名对照 `TOOL_REGISTRY` 校验（非法条目丢弃 + warning），坏文件降级保留上一份配置。语义样本变更需重算 embedding，调 `POST /api/v1/knowledge/router/reload`（admin）生效。

学习重点：看 `route()` 返回的 `method` 字段（rule/semantic/llm），再对照后端日志（`[SemanticRouter] intent=... score=... margin=...`）统计三级命中比例——这是面试讲"如何降低 LLM 成本"的第一手数据。阈值不要拍脑袋改：先跑 `scripts/tune_router_thresholds.py`，看各阈值下的覆盖率/准确率报告再决策。

### 5.2 RAG 检索管线（agents/rag.py + core/rag/engine.py）

职责分层是这个模块最重要的设计：

- **RAGAgent（策略层）**：`prepare_retrieval()` 做 Query 三分类（specific 直检+同义词扩展 / ambiguous 走 HyDE / broad 拆子问题）和复杂度分析；`execute_retrieval()` 编排多查询检索、CRAG 重试、Self-RAG 过滤。
- **RAGEngine（数据管道层）**：`search()` 只做一次检索的执行——L1/L2 缓存检查 -> 向量检索（Milvus，3 次重试）-> BM25 -> Graph RAG 实体子图注入 -> RRF 融合 -> 低分过滤 + Jaccard 去重 -> Reranker 精排 -> 置信度 + 冲突检测。

关键机制逐个说：

**类型感知 RRF 融合（`_merge_results()`）**。基础公式 `score = Σ weight/(K + rank)`，K=90。权重按查询类型调整：含编码/数字的 precise 查询等权（1.25/1.25），含"怎么/如何"的 semantic 查询向量加权到 2.25，默认 BM25 略重（1.75）。所有权重从 settings 读取，可用 eval 集调参。

**CRAG 检索质量反思**。检索后 `CriticEvaluator` 用关键词覆盖率 + top 分数评估质量；判定 low 时 `QueryRewriter` 改写 Query 重检一次，合并结果后再评估，只有改善才采纳。流式与非流式链路共用这一实现（`execute_retrieval()` 单一入口，有防回潮测试）。

**Self-RAG 过滤**。结果 >=4 条时用 LLM 逐 chunk 判断是否真正支持回答（阈值 0.15），过滤噪声。LLM 失败则跳过降级。

**四层后处理**（面试高频，注意分散在不同位置）：低分过滤 + Jaccard 去重在 `_merge_results()` 的后处理段；多源冲突检测在 `search()` 精排后（`_detect_conflicts()` 提取"实体+数值"对，同实体不同数值即标记）；可信度护栏在独立的 `keyword_coverage` 模块（生成后校验回答与上下文的关键词覆盖率）。

**降级链**：embedding 失败 -> 纯 BM25；Milvus 失败 -> 空向量路；Reranker 未启用 -> 按 RRF 分数排序；Neo4j 未连接 -> 跳过图谱路。每层降级都有 logger.warning，绝不静默。

**同步引擎 + 异步应用的边界**：`RAGEngine.search()` 是同步函数（pymilvus/embedding/CrossEncoder 都是同步 SDK），所有 async 调用点必须用 `asyncio.to_thread()` 包裹，否则会阻塞事件循环拖垮 SSE 并发——这是项目踩过的坑，也是并发压测验证过的点。

### 5.3 四层缓存架构（core/cache_manager.py）

```Plain Text
请求 -> L1 进程内 LRU（md5(query+top_k+doc_ids+vis_expr)，256条/300s）
     -> L2 Redis 语义缓存（余弦>=0.92，600s/200条，跨实例共享）
     -> L3 Redis 数据查询缓存（Text-to-SQL 60s / 只读工具 30s）
     -> 真实检索/查询
L4：nginx 静态资源缓存（vite hash 产物 immutable 1年，index.html no-cache）
```

`cache_manager.py` 是统一门面：各层读写入口 + hits/misses 命中率计数，`GET /chat/cache/stats`（仅 admin）可实时查看。

**L2 的存储模型值得细看**（semantic_cache.py）：向量集中存在单个 Redis Hash 索引（field=md5(query)，value 含 embedding + 知识库版本号 v），`lookup()` 一次 HGETALL 取回全部向量 -> numpy 矩阵乘批量余弦 -> 取最优 field 单次 GET 结果。网络往返固定 3 次（版本号 GET + HGETALL + 结果 GET），替代了旧版全量 SCAN + 逐 key GET 的 O(n) 模型（200 条时 200+ 次往返）。结果 key 靠 TTL 过期，索引 field 在 lookup 发现过期/旧版本时惰性清理。

**一致性失效**（防脏数据的三条规则）：

- 知识库上传/删除/批量入库成功 -> `l1_clear()` + `l2_invalidate()`。L2 的失效是 **O(1) 版本号机制**：`INCR scqa:kb:version`，旧版本条目下次 lookup 时被跳过并惰性清理，不再 SCAN 全清（`purge()` 保留 SCAN 作运维兜底）。
- 写工具（create_ticket）成功 -> `l3_invalidate("tool")` 清命名空间。
- L3 用 `cache_if` 谓词拒绝缓存错误结果。

**实测效果**（本机 Redis 环境，DEMO_MODE，benchmark_cache.py 输出）：冷启动 P50=7261ms -> L1 命中 P50=31ms -> L2 语义命中 P50=15ms。

Redis 不可用时所有缓存层直通降级，绝不抛错阻断主链路。

### 5.4 认证授权与行级 RBAC（core/auth.py + milvus_client.py）

**认证**：PBKDF2-SHA256（10 万次迭代 + 随机 salt）存密码；JWT HS256 签发（payload 含 user_id/username/jti/exp，24h）；登出把 jti 写入 Redis 黑名单（TTL=剩余有效期）——无状态验签 + 可主动撤销两者兼得。`REQUIRE_AUTH_CHAT=true` 时对话接口强制登录。

**行级 RBAC**：不建独立权限表，权限直接存在 Milvus 的 `security_group` ARRAY 列上，检索时 `build_visibility_expr(role)` 生成过滤表达式：

```Plain Text
非 admin：(array_contains(security_group, "<role>") or array_contains(security_group, "public"))
admin：空表达式（全可见）
```

好处：检索与权限过滤在同一次 Milvus 查询内完成，无额外 JOIN。BM25 内存索引侧用 `_roles_from_visibility_expr()` 提取角色做同等过滤，保证两路召回权限一致。

**两个安全要点**（都有专项测试）：

- 上传时的 `security_group` 由服务端根据当前用户角色权威裁决（非 admin 强制为自身角色），前端传什么都不信任——否则任何人可把文档挂到别的部门名下。
- 表达式中的 role/doc_id 全部白名单正则校验 + 转义，且 doc_ids 在 Pydantic 请求模型层提前拦截（SSE 开始后无法再返回错误状态码）。

### 5.5 工具系统与 Agent 链路（core/tool_engine.py + agents/tool.py）

`TOOL_REGISTRY` 注册 11 个工具：

| 类别 | 工具 |
|---|---|
| 业务查询 | query_inventory / query_order / query_supplier / track_logistics |
| 业务写入 | create_ticket（工单 ID：TK-{时间戳}{7位随机}，防高并发 UNIQUE 碰撞） |
| 智能计算 | calculate_reorder_point（ROP 模型） |
| 知识检索 | get_knowledge（代理 RAG 引擎） |
| 通用 | get_datetime / web_search / calculator（AST 白名单）/ code_interpreter（沙箱） |

设计要点：

- 全部 async，业务数据来自 aiosqlite 连接的本地 SQLite（Odoo 风格表）。
- 前端不再硬编码 Schema：`GET /tools/schema` 从 `TOOL_REGISTRY` 的 `args_schema` 动态生成，新增工具注册一处即可全链路可见。
- 工具权限按角色配置在 `api/tool.py` 的 `ROLE_TOOLS`。
- `code_interpreter` 的沙箱是双保险：AST 白名单预检（拒绝 import/危险属性/global/del）+ 受限 builtins。

TOOL_CALL 意图的执行流（tool_call.py handler）：参数澄清检查 -> 角色权限校验 -> 写操作人工审批（approval_request 事件，前端确认后带 approved 重发）-> Redis 幂等抢占 + 分布式锁 -> LangGraph ReAct 循环（最多 5 轮，死循环熔断器监控推理路径签名）。

### 5.6 Text-to-SQL（core/text_to_sql.py）

`/chat/sql` 端点的 NL2SQL 引擎，安全防护五层：只允许 SELECT -> 危险关键词黑名单 -> 表名白名单（users/tickets/feedbacks/eval_results）-> 字面值提取转绑定参数（参数化执行防注入）-> LIMIT 100 + 5s 超时。失败时把错误反馈给 LLM 自纠正一次。成功结果按 md5(sql) 进 L3 缓存 60s。

### 5.7 Graph RAG（core/neo4j_client.py）

两个用途：

- **检索增强**：`RAGEngine.search()` 中正则提取实体编码（MAT-xxx/PO-xxx/SUP-xxx，含 O->0 拼写自愈归一化），调 `get_2hop_subgraph_context()` 取 2-hop 关系并转成声明式自然语言，经 Critic 关键词重叠检查后作为伪 chunk 注入精排。
- **GRAPH_QUERY 意图**：graph_engine 走模板化 Cypher 做跨实体推理。

CLAUDE.md 硬约束：Cypher 必须模板化生成 + 参数绑定，禁止 LLM 直接生成（防幻觉查询）。图谱数据启动时从 SQLite 用 MERGE 幂等同步。

### 5.8 对话记忆（core/redis_client.py ChatMemory）

Redis List 存最近 N 轮（MEMORY_WINDOW=10），单 pipeline 合并 5 个命令；每 10 条触发后台 LLM 摘要压缩。key 设计 `scqa:chat:{user_id}:{session_id}`，匿名会话落入 `anon` 前缀空间——同一 session_id 不同用户互相读不到历史（会话窃取防护，有测试）。

| 业务模拟数据 | backend/app/data/supply_chain.db（SQLite） | 工具查询的数据源 |
| L2/L3 缓存、对话记忆、JWT 黑名单、限流、幂等锁 | Redis | 键前缀 scqa:* |
| 知识库源文件 | knowledge/*.md + backend/uploads/ | 入库脚本 backend/scripts/ingest_pdfs.py |
| trace | Langfuse（自托管，PG 存储） | span 级链路 |

### 6.1 关键设计取舍

| 设计 | 好处 | 代价 |
|---|---|---|
| Milvus ARRAY 做行级 RBAC 而非独立权限表 | 检索与过滤一次查询完成，无 JOIN | 权限变更需重写向量记录的字段 |
| RRF 融合而非加权求和 | 不依赖分数归一化，对不同检索器分数尺度鲁棒 | K 与路权重需要 eval 集调参 |
| 模板化 Cypher 而非 LLM 生成 | 查询永远合法，无幻觉 | 只支持预设查询模式 |
| BM25 内存索引 | 零外部依赖、检索快 | 多 worker 各持一份，重启需全量重建 |
| 同步检索引擎 + to_thread 边界 | 不必重写 pymilvus/CrossEncoder 调用链 | 每次检索占一个线程池线程 |
| SSE 而非 WebSocket | 单向流足够、HTTP 语义简单、nginx 易配 | 客户端到服务端只能靠新请求 |
| L1 进程内缓存 | 零网络开销 | 多 worker 不共享，一致性靠 TTL+全清 |
| llama.cpp 本地部署 | 数据不出网，符合企业敏感场景 | 需要本地 GPU/内存资源 |

生产环境（docker-compose.prod.yml）：

```Plain Text

```

与开发版的关键差异：

- nginx 统一入口（SSE 需 `proxy_buffering off`，已配好；静态资源 L4 强缓存 + 安全头）。

## 如何扩展项目

### 8.1 新增一个业务工具

以"查询物料成本"为例：

1. 在 `backend/app/core/tool_engine.py` 用 `@tool` 装饰器定义 async 函数，docstring 写清用途和参数（LLM 靠它决定是否调用）。
2. 在 `TOOL_REGISTRY` 加一行注册。
3. 在 `backend/app/api/tool.py` 的 `ROLE_TOOLS` 给相关角色开权限。
4. 只读查询类工具用 `_l3_tool_cache()` 包一层 L3 缓存；写类工具成功后调 `_invalidate_tool_cache()`。
5. 前端不用改——`/tools/schema` 会自动带出新工具。
6. 补测试：正常路径、空输入/不存在编码、（如适用）缓存命中与失效。

工具设计建议：返回 JSON 字符串；错误装在 `{"error": ...}` 里而不是抛异常（错误结果不会进缓存）；数据库连接用 `_get_conn()` 并在 finally 关闭。

### 8.2 新增一个意图 handler

1. 在 `backend/app/agents/router.py` 的 `IntentType` 加枚举，并在 `backend/app/data/intent_routes.json` 加识别规则（关键词/实体规则热加载即生效；语义样本需调 `POST /knowledge/router/reload` 重建 embedding）。
2. 在 `backend/app/api/handlers/` 新建 `<intent>.py`，签名模式：依赖全部参数注入，返回 `AsyncGenerator[str, None]`，只 yield `sse_event(...)`。
3. 在 `handlers/__init__.py` 导出，在 `chat.py` 的意图分发段加一个 elif。
4. 补 handler 单测（mock 依赖，覆盖正常/空输入/降级）——参照 `tests/test_handlers_extended.py` 的写法。

### 8.3 新增知识库文档

1. 在 `knowledge/` 按 `SC-{部门}-{序号}.md` 命名新建文档。
2. 走前端 Knowledge 页上传，或调 `POST /knowledge/upload`——注意权限组由服务端按登录角色裁决，非 admin 上传的文档只对自己部门可见。
3. 上传成功即自动完成：切片（256/128）-> 嵌入 -> Milvus 入库 -> BM25 增量索引 -> L1 全清 + L2 版本号失效。
4. 验证：用对应部门账号提问能召回，用其他部门账号提问不可见。

### 8.4 调整检索参数并评估

1. 参数全在 `config.py`（RRF_K、各路权重、top_k、阈值），可经 `.env` 覆盖。
2. 改动后跑 `backend/eval/` 的评估集对比检索指标，不要凭感觉调参。
3. 注意约束：`RRF_MIN_SCORE` 必须小于最小单路分数 `min_weight/RRF_K`，否则单路召回结果会被全量过滤（历史 bug，config 注释里有说明）。

## 常见问题排查

### 9.1 后端启动失败或功能降级

按 lifespan 日志逐项看：

1. `[SECURITY]` RuntimeError -> DEBUG=false 但仍在用默认密码/CORS *，按提示设环境变量。
2. Milvus 连接失败 -> RAG 不可用但服务仍启动；检查容器和 19530 端口。
3. `InvalidKeyError` / HMAC 告警 -> `.env` 缺 JWT_SECRET 或长度 <32 字节。
4. PostgreSQL 密码错误 -> 旧数据卷密码与 .env 不一致，容器内 `ALTER USER ... PASSWORD` 或换卷。
5. BM25 重建失败 -> Milvus collection 为空属正常，先入库。

### 9.2 提问没有走预期链路

- 永远命中缓存 -> 看 `cache_hit` 事件；改一个字重问，或 admin 调 L2 invalidate。
- 意图判错 -> 看 `route` 事件的 method 字段；规则层误命中就改 `app/data/intent_routes.json`（热加载，不用重启）；语义层误判先看日志里的 score/margin，再用 tune_router_thresholds.py 验证阈值。
- 检索为空 -> 依次确认：该角色对文档可见（Attu 看 security_group）、embedding 模型加载成功（日志）、BM25 已重建。
- 回答"服务暂时不可用" -> llama.cpp 未启动或熔断器打开（连续失败 5 次熔断 30s）。

### 9.3 测试相关

- 单测不需要任何 Docker 服务；`conftest.py` 已注入测试 JWT_SECRET 并关闭 REQUIRE_AUTH_CHAT。
- 集成测试标记 `@pytest.mark.integration`，默认 deselect。
- 覆盖率低于 70% 会直接失败——新增代码必须带测试。
- async 测试直接写 `async def test_xxx()`；禁止在测试里 `asyncio.run()`（嵌套 event loop）。

### 10.2 高频追问与要点

| 追问 | 回答要点 |
|---|---|
| 为什么 RRF 不是加权求和 | 不同检索器分数尺度不可比（余弦 vs BM25 raw），RRF 只用排名，天然鲁棒 |
| RRF_K 为什么是 90 | 平滑常数，K 越大头部排名差异越被抹平；这是 eval 集调参结果，不是拍脑袋（注意：不要说成 60，旧文档写错过） |
| 缓存一致性怎么保证 | 三条失效规则（知识库变更清 L1 + L2 版本号 INCR 失效、写工具清 L3、错误结果不缓存）+ TTL 兜底；L2 用 epoch 版本号避免 SCAN 全清，失效 O(1)；L1 多 worker 不共享是已知取舍 |
| 权限为什么不建表 | 检索与过滤同一次查询完成；代价是权限变更要改向量记录——适合"部门级、低频变更"场景 |
| 同步 SDK 怎么不阻塞 | to_thread 边界包裹；有并发压测证据（压测中轻量端点 P95 不劣化） |
| 幻觉怎么控制 | 检索侧 Self-RAG 过滤 + 冲突检测提示；生成侧低置信度严格 Prompt；生成后关键词覆盖率护栏 <0.5 报警 |
| 写操作怎么保证安全 | 澄清->RBAC->人工审批->Redis 幂等抢占->分布式锁->ReAct 熔断，五道闸 |

### 10.3 诚实边界（被追问时不要硬撑）

- RAGAS 指标要格外小心：仓库历史评测 `ragas_comparison_final.json`（Qwen2.5 时期、LLM-judge）实际是 Context Precision 0.51 / Faithfulness 0.80 / Answer Relevancy 0.52 / Context Recall 0.73、Overall 0.64（文件自标 `all_above_075: false`），**四项从未同时 >0.82**；简历/旧文档里的 0.82/0.88 大概率是把检索指标（RRF Precision 0.84 / NDCG 0.98）误当成了 RAGAS。要写 RAGAS 数字请先用真正的 LLM-judge 重跑 `backend/eval/` 验证，否则改用可实证的检索指标（MRR 0.92 / NDCG 0.98 / Precision 0.84）。
- L1 是进程内缓存，多 worker 部署各持一份，一致性依赖 TTL——没有做跨进程失效广播。
- BM25 删除文档时全量重建索引，知识库高频增删场景会是瓶颈。
- Milvus 索引是 IVF_FLAT/nlist=128，数据量到百万级需要评估 HNSW。
- 没有做用户级细粒度权限（只有部门角色级）；没有多租户。

### 10.4 面试问答卡：CRAG 改写重检 + Self-RAG 逐 chunk 过滤

这两个机制常被问，且很容易因“听起来像论文完整实现”而被追问拆穿。下面是可直接背的话术与诚实边界。

**Q：你怎么控制幻觉？（完整话术）**

> “检索和生成两侧都做了控制。检索侧两个机制：一是 CRAG——检索完先用轻量规则评估这批结果质量（关键词覆盖率 + rerank 分数），不达标就改写查询重检一次，避免把差的上下文塞给模型；二是 Self-RAG 思想的相关性过滤——用 LLM-as-Judge 给每个 chunk 打分，过滤掉不相关的，只留干净上下文。生成侧：低置信度走更严格的 Prompt，生成后还有关键词覆盖率护栏（<0.5 报警）。三层叠加把幻觉压下来。”

**Q：CRAG 是什么？用大模型改写吗？**

- 是什么：Corrective RAG，检索质量不好就纠正（改写重检）而非硬用。参考 Agentic RAG 论文（arXiv:2501.09136）。
- 我的实现（`core/rag/critic.py`）：`CriticEvaluator` 用**轻量规则、不调 LLM**——关键词覆盖率 + 最高 rerank 分数 + 有效结果数，分 high/medium/low（阈值 0.6/0.3）；不达标时 `QueryRewriter` **规则式改写**（去掉“是多少/怎么/如何”等疑问词扩大检索，或从 top 结果补 1-2 个缺失关键词），最多重检 1 次，改善才采纳。
- 诚实点：Critic 和改写**都是规则、零额外 LLM 开销**——别说成“LLM 改写查询”。

**Q：Self-RAG 你实现了论文吗？**

- 是什么：检索后逐 chunk 判断相关性，过滤噪声。
- 我的实现（`core/llm_relevance.py`）：LLM-as-Judge 给每个 chunk 打 0-1 分，低于阈值（`LLM_RELEVANCE_THRESHOLD=0.15`）过滤；仅 chunk 数 >1 时启用，LLM 失败优雅降级。
- 诚实点（关键，代码注释里就写了）：这是**借鉴 Self-RAG 思想，不是论文完整版**。论文要训练 LLM 输出 reflection token（`[Retrieve]/[IsRel]/[IsSup]`），我没训练、也没有 token，只是“LLM 打分 + 阈值过滤”。被追问务必这么讲。

**Q：CRAG 和 Self-RAG 区别？**

| | 作用点 | 用 LLM | 管什么 |
|---|---|---|---|
| CRAG 改写重检 | 检索层（整批） | 否（规则） | 结果差 → 改写查询重检 |
| Self-RAG 过滤 | 过滤层（逐条） | 是（打分） | 哪些 chunk 留/丢 |

一句话：**CRAG 管“要不要重检”，Self-RAG 管“哪些 chunk 留下”**；前者规则、零成本，后者调 LLM。两者都是“让喂给生成模型的上下文更干净”，但一个在检索环节纠错、一个在过滤环节去噪。

## 最后复盘

如果只记住一条主线，请记住：

用户提问先经过 PII 脱敏和 JWT 认证，Query Cache 命中就零 token 直接返回；未命中则三级意图路由决定走哪条链路。知识类问题进入统一检索管线：策略层准备查询（HyDE/子问题），引擎层三路召回并 RRF 融合，CRAG 和 Self-RAG 做两轮质量反思，行级 RBAC 表达式保证每个部门只看到自己的文档；置信度决定直答、改写重检还是外部搜索，LLM 流式生成的每个 token 经 SSE 推给前端，最后写回缓存和按用户隔离的对话记忆。业务类问题则走澄清、权限、审批、幂等、锁五道闸后进入 ReAct 工具循环。

这个项目最值得学习的不是某一个算法，而是这一整套闭环：

- 可运行（一键启动 + 降级链保证部分服务缺失也能跑）。
- 可测试（handler 纯函数式 + 依赖注入 + 70% 覆盖率门禁）。
- 可观测（SSE 事件流 + 结构化日志 + Langfuse trace + 缓存命中率端点）。
- 有权限边界（JWT + 行级 RBAC + 服务端权威裁决 + 注入防护）。
- 有性能边界（4 层缓存 + 事件循环隔离 + 熔断限流）。
- 有质量边界（CRAG + Self-RAG + 冲突检测 + 覆盖率护栏）。

理解这个闭环，你就理解了一个企业级 RAG + Multi-Agent 系统的核心设计。
