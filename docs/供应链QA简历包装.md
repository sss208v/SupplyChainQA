## 浅显面试讲法

这个项目主要解决两个问题：第一，企业员工要查供应链数据得在库存、订单、制度等多个后台系统之间来回切换；第二，直接套通用 RAG 会遇到检索不准、答非所问、没有权限隔离的问题。

我做的是一个**双链路智能问答系统**。员工用大白话提问，系统会自动判断该走哪条路：问"采购审批流程是什么"这类知识问题，就去知识库检索制度文档生成答案；问"查一下 MAT-001 还剩多少库存"这类业务问题，就直接调用工具查实时数据、甚至帮你创建工单。

判断走哪条路用的是三级路由：能用规则秒判的（比如带物料编码的库存查询）就零成本直接分流，规则拿不准的用向量相似度判断，都不确定才交给大模型。这样绝大多数请求不花大模型的钱。

检索侧我做了三路召回加融合，还加了两轮质量反思——检索不好会自动改写问题重查，答案生成前会逐段过滤不相关内容，生成后还会校验有没有编造。另外每个部门只能看到自己权限内的文档，重复问题会命中缓存零成本重放，知识库一更新缓存会自动失效。

## 深度讲法

系统入口是 `/api/v1/chat/stream` 的 SSE 流式接口。请求先过 PII 脱敏、JWT 认证和限流，再查一层精确缓存（命中就零 token 重放），未命中进入三级意图路由。

**三级路由**是 hybrid routing 思路：规则层只做确定性短路，按优先级依次匹配问候、实体编码（`MAT-/PO-/TK-` 编码 + 关系词走图谱、编码 + 领域提示词走工具）、精确命令词、目标型关键词、高精度知识问句正则——这里特意删掉了旧版 100+ 领域泛词大表，因为像"库存""采购"这种泛词会抢在语义层之前碰撞误判（比如"MAT-001 还剩多少库存"会被"库存"错判成知识检索）。规则未命中下沉到语义层，用 embedding 余弦匹配意图样本，两道门槛：分数 ≥ 阈值（全局 0.65，支持 per-intent 覆盖）且 top1-top2 分差 ≥ margin 0.03，不满足才回退 LLM。路由关键词和语义样本全部外置到 `intent_routes.json`，`intent_routes.py` 按 mtime 热加载、对照 `TOOL_REGISTRY` 校验工具名，语义样本变更后走 admin 的 `/knowledge/router/reload` 重建 embedding；阈值不拍脑袋，用 `tune_router_thresholds.py` 离线扫描覆盖率/准确率再定。

**检索链路**分策略层和数据管道层。RAGAgent 做 Query 三分类（specific 直检 / ambiguous 走 HyDE / broad 拆子问题）和复杂度分析；RAGEngine 做一次检索的执行：向量（Milvus，3 次重试）+ BM25 + 图谱实体子图三路召回，用类型感知 RRF 融合（`score = Σ weight/(K + rank)`，K=90，权重按查询类型调整），再低分过滤 + Jaccard 去重 + Reranker 精排。质量侧 CRAG 用 CriticEvaluator 评估、低质量触发 QueryRewriter 改写重检一次，Self-RAG 用 LLM 逐 chunk 过滤（阈值 0.15），生成后 keyword_coverage 护栏做忠实度校验。注意 RAGEngine 是同步引擎（pymilvus/CrossEncoder 都是同步 SDK），所有 async 调用点用 `asyncio.to_thread()` 隔离，否则会阻塞事件循环拖垮 SSE 并发。

**权限**不建独立表，直接把 `security_group` 存成 Milvus ARRAY 列，检索时用 `build_visibility_expr(role)` 生成 `array_contains` 过滤表达式，检索和过滤在同一次查询完成；BM25 内存索引侧同步做角色过滤，保证两路权限一致。

**缓存**是多层门面：L1 进程内 LRU、L2 Redis 语义缓存、L3 查询结果缓存。L2 值得细讲——向量集中存单个 Redis Hash 索引（一次 HGETALL + numpy 批量余弦，替代旧版 O(n) 的 SCAN + 逐 key GET），失效用知识库版本号 `INCR scqa:kb:version` 实现 O(1)，旧版本条目在下次 lookup 时被跳过并惰性清理，不再全量 SCAN。

**Agent 链路**走 LangGraph ReAct（最多 5 轮，死循环熔断器监控推理路径签名），写操作经澄清 → RBAC → 人工审批 → Redis 幂等三态抢占 → 分布式锁五道闸，工单 ID 用 `TK-{时间戳}{7位随机}` 防高并发 UNIQUE 碰撞。全程 SSE 推 7 种事件，Langfuse 做 span 级 trace。

## 面试高频问题和回答

### Q1：为什么要做三级意图路由，而不是直接用 LLM 分类？

成本和延迟。LLM 分类每次 ~2.5s 且（云端场景）消耗 token。三级路由让规则层 <1ms、语义层 <10ms 且零 token 就拦截掉绝大多数明确请求，只有前两级都不确定时才回退 LLM。看 `route` 事件的 `method` 字段（rule/semantic/llm）就能统计三级命中比例，这是"如何降低 LLM 成本"的第一手数据。

### Q2：三级路由怎么避免"查库存"被误判成知识检索？

这正是我重构时修的坑。旧版规则层有 100+ 领域泛词大表，"库存""采购"这种词会抢在语义层前面碰撞误判——"MAT-001 还剩多少库存"会被"库存"短路成知识检索。我改成**实体编码优先**：含 `MAT-/PO-/TK-` 编码时先判关系词（走图谱）、再判领域提示词（走工具），并删掉泛词大表让模糊问句下沉到语义层。这样带编码的库存查询正确路由到工具，而"MAT-001 的质检标准是什么"这种知识问句仍走 RAG。

### Q3：RRF 为什么不用加权求和？

不同检索器的分数尺度不可比——向量是余弦相似度、BM25 是词频 raw 分，直接加权求和需要先做分数归一化，很脆弱。RRF 只用排名（`Σ weight/(K + rank)`），天然对分数尺度鲁棒。K=90 是平滑常数，K 越大头部排名差异越被抹平，这个值和各路权重都是用 eval 集调参出来的，不是拍脑袋。

### Q4：CRAG 和 Self-RAG 有什么区别？

两者都是质量反思但作用点不同。CRAG 是**检索后**评估整批结果质量，低质量时改写 Query 重检一次、合并后再评估，只有改善才采纳；Self-RAG 是**逐 chunk** 用 LLM 判断每段是否真正支持回答（阈值 0.15），过滤噪声。一个管"要不要重新检索"，一个管"哪些片段该保留"。两者 LLM 失败都跳过降级，不阻断主链路。

### Q5：行级权限为什么不建独立权限表？

因为检索和权限过滤要在同一次查询完成。我把 `security_group` 直接存成 Milvus 的 ARRAY 列，检索时用 `array_contains` 生成过滤表达式，一次向量查询就带权限，没有额外 JOIN。代价是权限变更要改向量记录的字段——适合"部门级、低频变更"的场景。BM25 内存索引侧也做同等角色过滤，保证两路召回权限一致。

### Q6：多层缓存怎么保证一致性？

三条失效规则 + TTL 兜底：知识库上传/删除/入库成功清 L1 + L2、写工具成功清 L3、错误结果不进缓存。重点是 L2 的失效——我用知识库版本号 `INCR scqa:kb:version` 实现 O(1) 失效，旧版本的缓存条目在下次 lookup 时被识别为 stale 跳过并惰性清理，不用像旧版那样 SCAN 全量删除（`purge()` 保留 SCAN 作运维兜底）。L1 是进程内缓存、多 worker 不共享，一致性靠 TTL——这是已知取舍。

### Q7：写操作怎么保证并发安全？

五道闸：参数澄清检查 → RBAC 工具权限 → 写操作人工审批（前端确认后带 approved 重发）→ Redis 幂等三态抢占（SET NX 原子）→ token 分布式锁（Lua 原子释放）。工单 ID 用 `TK-{时间戳}{7位随机}`，后缀 ≥7 位防高并发 UNIQUE 碰撞。这样同一请求重复提交不会重复建单。

### Q8：项目最大的技术难点是什么？

难点不是调某个 API，而是把意图路由、混合检索、质量反思、权限、缓存、并发安全、可观测这么多子系统串成一个稳定闭环，还要每一层都有降级路径。举两个具体的：一是异步纪律——RAGEngine 是同步 SDK，必须用 `to_thread` 隔离否则阻塞事件循环拖垮 SSE 并发，这是压测验证过的；二是路由准确率与成本的平衡——既要前两级多拦截省 token，又不能误路由，所以引入了实体优先、margin 判据和离线阈值调参。

## 简历 bullet 精简池

下面这些 bullet 可以按岗位选择组合。

### 意图路由与分流

- 设计三级级联意图路由（规则 → 语义 embedding → LLM 兜底），前两级零 token 拦截绝大多数请求，显著降低 LLM 调用成本。

- 将路由关键词、实体规则与语义样本外置到配置文件，支持 mtime 热加载、工具名校验与 admin 在线重载，新增工具只改配置不改代码。

- 引入实体编码优先匹配与 top1-top2 margin 判据，修复领域泛词碰撞导致的路由误判，并用离线脚本扫描阈值替代经验配置。

### 混合检索与质量反思

- 构建向量 + BM25 + 图谱三路召回，采用查询类型感知的自适应 RRF 融合，配合低分过滤、Jaccard 去重与 BGE-Reranker 精排。

- 实现 CRAG 检索反思（低质量触发 Query 改写重检）与 Self-RAG 逐 chunk 相关性过滤，生成后用关键词覆盖率护栏做忠实度校验。

- 集成 Neo4j GraphRAG，用模板化 Cypher（不让 LLM 直接生成）做多跳实体关系检索；构建实体链接词典（中文实体名→图谱查询键，配置外置 + mtime 热加载）把图谱路触发面从编码正则扩展到自然语言提问，伪 chunk 按实体拆分逐个过 Critic 参与精排，图谱子集注入率 100%*。

### 评测与质量闭环

- 基于官方 RAGAS 0.4.3 建立可信评测体系：生成（本地 Qwen3-14B）与评判（DeepSeek judge）分离，评测集经 LLM 核验 + 人工审核双重把关，每次实验 ×3 取 mean±std，先量化指标噪声带再判定改动有效性。

- 通过语料冲突治理与评测口径修正提升评测可信度，再经精排分数截断扫参发现"更少更精上下文抬升生成忠实度"的杠杆，Context Precision 0.700→0.76、Faithfulness 0.70→0.76，四项指标全部达标、综合 0.84*；未达预设门槛的优化（两轮 prompt A/B）按判定纪律否决回滚，不拿噪声当收益。

### 权限与并发安全

- 基于 Milvus `security_group` ARRAY 列 + `array_contains` 实现行级 RBAC，检索与权限过滤一次查询完成，不引入独立权限表。

- 为写操作设计澄清 / RBAC / 人工审批 / Redis 幂等 / 分布式锁五道闸，保证高并发下工单不重复创建。

- 实现 JWT 无状态验签 + Redis jti 黑名单可撤销 + PBKDF2 密码哈希的认证体系。

### 缓存与性能

- 设计多层缓存（进程内 LRU / Redis 语义缓存 / 查询结果缓存），命中率经统一门面实时统计。

- 用 Redis Hash 向量索引 + numpy 批量余弦把语义缓存网络往返从 O(n) 降为常数级。

- 以知识库版本号 INCR 实现 L2 缓存 O(1) 主动失效，替代全量 SCAN，知识库更新即时生效。

- 将同步检索引擎经 `asyncio.to_thread` 隔离，保证 SSE 高并发下不阻塞事件循环（并发压测验证）。

### 可观测与工程化

- 实现全链路 SSE 流式输出（7 种事件类型）+ Langfuse span 级 trace + LLM 熔断/重试/多级降级链。

- 建立 1000+ 单元测试、覆盖率 >70% 的 CI 门禁*，handler 采用纯函数式 async generator + 依赖注入，可独立 mock 单测。
